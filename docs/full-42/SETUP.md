# Setup: cloud, permissions once, deploys, access, cost guards

The old build lost days to IAM: 134 bindings across seven amendments, each approved on its own, plus expiring roles and hand renewals. The new core needs one small set of identities, created once by one add-only script, and then nothing changes. Role names checked against Google's documentation on 28 September 2026.

## Where things live

- Staging: project ogilvy-trends-v2, region us-central1, BigQuery location US. New datasets intelligence_42_core (posts, enrichment, clusters, cultural map, detection, ledger) and intelligence_42_agent (runs, findings, forecasts, feedback). Existing datasets are read, never changed or deleted.
- Production: a separate project Albert creates when stage 3 is done (suggested ogilvy-42-prod), with the same layout. Nothing is built there without Albert's written word.
- Bucket: gs://ogilvy-trends-v2-f42-media-staging for clips, keyframes and exports, created with a 30-day soft-delete policy as a backstop.
- Container images: the existing Artifact Registry repository intelligence-42.
- Secret: the existing SOCIALCRAWL_OGILVY_API_KEY. A second, CHANNEL_WEBHOOK_URL, is declared by bootstrap.py for the team channel's incoming-webhook address (core/api/contract.md 14.3), readable by f42-agent only, but the channel post is not wired: no job mounts it (f42-scheduled-asks carries only the SocialCrawl key), it has no version, and no webhook is to be created. A third, GMAIL_APP_PASSWORD, holds the Gmail app password of jhb.analytics@gmail.com for the daily alert email digest (BUILD.md 2.9, core/api/digest.py --send); Albert creates it and sets its value, bootstrap.py grants f42-agent secretAccessor on it only once it exists, and it is mounted only on the job f42-digest, never printed, logged or recorded. The job sets GMAIL_USER in its env; DIGEST_RECIPIENTS (comma-separated plain addresses, sent as blind copies) and DIGEST_SEND_ENABLED=true are set by hand on the deployed job, and it sends nothing until both are. It sends at most once a day, recorded as runs rows with stage digest.

## The bootstrap script

core/setup/bootstrap.py (Python 3.13, uses gcloud and the BigQuery client with Albert's own login; the only script that ever grants). Behaviour:
- Default is a dry run that prints every create and grant it would make and which already exist.
- --apply performs only additions: create missing accounts, datasets, bucket, connection, pool and provider, add missing bindings. The one in-place change is the staging provider's attribute condition, patched alone and only when the new condition narrows the live one; the pool and provider are never recreated. On today's staging a run changes only that condition; the held f42-deployer grants above are not planned. It never removes or replaces a binding and never edits an existing dataset's access list wholesale (dataset grants use the BigQuery GRANT statement, which adds one entry).
- It is idempotent: running it again adds only what is new and changes nothing else.
- Ends with a readback that prints a table of every expected binding and whether it is present. Bootstrap counts as done only when a deployed smoke job per identity passes: each runs as its identity and does its real work in miniature (MERGE into a scratch table, ML.GENERATE_EMBEDDING on one row, read the mounted secret's length without printing it, read one object from the bucket, start the next job with an override that exits at once, one model call, one Scheduler run-now).
- Prints no secret values.

Albert runs it once in Stage 0: `py -3.13 core/setup/bootstrap.py` to see the plan, then `py -3.13 core/setup/bootstrap.py --apply`. If a later stage finds a missing binding, the builder adds it to bootstrap.py and Albert re-runs the same command; no other grant path exists, and add-iam-policy-binding is never run anywhere else.

## Deploys without anyone's PC

- GitHub Actions authenticates to Google Cloud with Workload Identity Federation (google-github-actions/auth@v3, permissions id-token: write). No keys are stored anywhere. The staging provider f42-github-staging only accepts tokens whose condition is `assertion.repository == 'jhbanalytics-pixel/42-Ogilvy-Intelligence' && assertion.ref == 'refs/heads/full-42' && assertion.event_name == 'push'`; bootstrap.py patches that condition alone on the existing provider when the live one is wider.
- On merge to the build branch: build each image once, push to intelligence-42, deploy to staging, run the smoke test. The image digest moves automatically; nobody pins anything by hand.
- Production: a separate workflow that only Albert can start (workflow_dispatch, with the production provider condition restricted to Albert's GitHub user id), deploying the exact image digest that passed staging. GitHub's required reviewers for private repositories need GitHub Enterprise; if the organisation has it, use a protected production environment instead.
- Until the Actions setup exists (Stage 3), the builder deploys staging from Albert's PC with `gcloud run deploy` as f42-builder, never with Albert's own login.
- The production workflow file is production.yml on main; the production provider accepts only a workflow_dispatch of that file on main, first attempt, started by Albert's GitHub user id.

| PULSE_DAILY | 60 credits for the intraday pulse, a share of its own outside ENGINE_DAILY (Albert, 29 September) | The pulse stops for the day |

| EVAL_DAILY | 0 live credits; evaluations run in replay mode from cached responses; 100 live for a deliberate refresh | The eval run |

| EVAL_MODEL_USD | USD 40 per evaluation run, counted apart from MODEL_DAILY_USD | The eval run stops and reports what it scored |

- SocialCrawl: ledger table intelligence_42_core.credit_ledger (run, job, agent, route, params hash, quoted and charged credits, balance), reconciled nightly with credits/transactions. Collect runs with one retry, so a failed run cannot spend twice. A separate dev key for build work is optional; until Albert buys one, BUILD_DAILY protects the funded key.
- Agent: per-tier max_budget_usd and max_turns; per-user daily question limit in the API; model spend logged per run and summed against MODEL_DAILY_USD.
- Google Cloud: budget alerts at 50, 90 and 100% of a monthly amount Albert sets, to Albert and a second person. Spend caps (preview) on Cloud Run in production.
- Cloud Run: max instances 3 for the app and agent, min 0; jobs with parallelism 1, an explicit task timeout and max retries 1. Schedulers use the Africa/Johannesburg time zone.

Expected monthly running cost (estimates from list prices on 28 September 2026, to be replaced by measured cost per answer and per morning in Stage 1A): SocialCrawl up to 80,000 credits (45,000 until 3 October 2026, a rate the existing balance covered for about five and a half months); Google Cloud infrastructure about USD 100 to 200; models between USD 800 and 3,500 depending on question volume and how often deep questions run, which is why MODEL_DAILY_USD exists. The estimates differ by that much, so measured numbers decide the default model per role. Transcripts for every clip would add about 150,000 credits a month, so 42 transcribes only clips that matter.

## Monitoring (as code, core/setup/monitoring.py and the f42-watchdog job in core/setup/watchdog.py, adapted from ops/monitoring/apply_monitoring.py)

Eight alerts, emailed to Albert and a second person: collection missing, job failed, brief not published by 06:30 SAST, credits low, model spend over 80% of MODEL_DAILY_USD, zero rows collected, schema drift on a SocialCrawl route, agent error rate over 5%; a ninth, reconcile, fires when the nightly ledger and vendor totals differ by more than 2 credits or 2%; a tenth, drift, fires when the weekly seed drift report (job f42-drift, Monday 07:00 SAST, as f42-collector with no SocialCrawl key) finds last week's expansion more concentrated than the open feeds on a topic, platform or language; an eleventh, seeds_failed, fires once a day when the day's latest seeds runs row (the seed queue writer inside f42-detect) is failed; a twelfth, agent_views_failed, fires once a day when the day's latest detect runs row records counts.agent_views.status 'failed', meaning f42-detect could not apply the views the API reads, and its line carries the error. Every job checks that the job before it finished for today's run before it starts, so the brief can never publish stale detection.

## Data protection (for Ogilvy legal to confirm; this is not legal advice)

42 collects public posts in three countries, so three laws apply: South Africa's POPIA, Nigeria's NDPA 2023 and Kenya's Data Protection Act 2019. Legal reviews all three before production, including whether Ogilvy must register with Kenya's ODPC and Nigeria's NDPC as a data controller for this use. The policy 42 follows from day one:

- Collect only what people deliberately made public; store handle and post id, never contact details; aggregate by default.
- Never classify individuals on religion, race, health, politics, sex life or crime (POPIA section 26). Stance on political or religious topics is shown only in aggregate, never tied to a handle, and the agent's views expose it only as aggregates.
- Link to clips and posts instead of copying media of private people; copy only clips from accounts at macro tier or above, brand accounts, or clips a dossier cites, for evidence that must survive deletion by the author. Keyframes kept for video reading follow the same rule.
- Requests from people to remove their data: suppress at once (a suppression list the whole system respects), and delete only on Albert's written word, logged. This is the one path by which data is deleted.
- No direct marketing. Operator agreements with SocialCrawl and Google (POPIA sections 21 and 72 for cross-border transfer).
- Retention of raw text follows the existing 90-day rule only if Albert approves it in writing, because expiry is deletion.
- Data sits in the US region under Google's data processing terms; Johannesburg (africa-south1) is the alternative if legal prefers, subject to model availability there. Platform terms restrict automated collection even through a vendor, and scraped public pages (for example the X trends archive) have their own terms; legal should review both.
- The daily alert email is the digest job (f42-digest, `core/api/digest.py --send`, 06:45 SAST), and this describes the flow as built. The job sends through Gmail SMTP (smtp.gmail.com, port 587, STARTTLS) from the project mailbox set as GMAIL_USER, logging in with the app password from Secret Manager, which is never printed or recorded. The message is addressed to that mailbox, and the recipients in DIGEST_RECIPIENTS go as blind copies, so no reader sees another. The recipient list is the DIGEST_RECIPIENTS setting, set by hand on the deployed job, and its value is not recorded in this document. Nothing sends unless DIGEST_SEND_ENABLED is true, and at most one digest is sent successfully a day. Each one lists, for each watch that fired, the topic title, its state, the count line, any held-back reason, up to two links to public posts with the creator handle and platform, and a link to the topic page, plus any waiting-for-data notes. The runs table keeps counts (recipients, alerts, waiting and refusals) and, on a failed send, only the exception type, never an address or the password. This note adds no new recipients, deliveries or exceptions.
