# Resource guard

R03 uses `ops/deploy/resource_guard.py` as a pure allowlist boundary. `load_resource_manifest` reads one regular, nonlink JSON file no larger than 1 MiB and requires the caller to supply the independently approved SHA256. It verifies the bytes before parsing, rejects duplicate keys and nonfinite values, then validates the closed `42_resource_manifest_v1` schema.

`assert_allowed` requires exact full resource-name membership and the requested action on that same row. It does not match prefixes, suffixes, project aliases or staging-looking names. Cloud Run and Cloud Scheduler names remain distinct because their service authorities differ. Secret containers and numeric secret versions are separate resources. Project IAM, secret IAM and the Cloud Build location parent also require their own rows.

Resource identifiers use separate service grammars. Cloud Run service IDs use lowercase letters, digits and hyphens, start with a letter, end with a letter or digit and stay below 50 characters. The selected Tasks, Scheduler, Artifact Registry and Cloud Build names use a documented restricted lowercase and hyphen subset capped at 63 characters. BigQuery datasets and routines, Secret Manager secrets, IAM custom roles, service accounts and Storage buckets each retain their own character and length checks. A character accepted by one service does not become valid for another.

The manifest requires the nine build, deploy, orchestration, app, ingestion, QA, scheduler, freshness and price-policy identities. Each value is a distinct full IAM service-account resource name in the declared project. Optional execution identities are closed to the reviewed purpose list. Identity spelling proves neither existence nor permission.

Review enrollment remains in the prepared state with no subjects or enrollment evidence. This guard performs no cloud request and grants no authority by itself. A native consumer must load exact approved bytes, check the requested resource and action, and separately bind the reviewed request body or IAM delta before dispatch.

No concrete `resource_manifest.json` is supplied by this implementation. Synthetic test manifests use computed fixture digests and are never native authority.

# Execution generation cutover

The migration script `engine/scripts/migrations/create_open_intelligence_execution_approval_store.py` carries three operator words for the prepared to ready cutover of the v2 execution store: `cutover-v2-preflight`, `cutover-v2-dry-run` and `cutover-v2-apply`. Each takes six options, once each and in any order: `--residuals PATH` (a JSON object whose `residuals` list carries one `consumption_id` per retained historical residual), `--v1-disable-receipt PATH`, `--inactivity-receipt PATH`, `--expected-v1-lock-version INT`, `--output PATH` and `--activation-phrase-file PATH`. The preflight also requires `--phase pre-disable` or `--phase post-disable`, with no default; the other two words refuse it. Any other shape, a repeated or unknown option, an empty value or a lock version that is not a plain non-negative integer refuses with `execution_approval_manifest_invalid` and exit code 2, the same emission the existing words use. Every word refuses an existing output path with `output_exists` before it reads any input, then writes its receipt to that path exactly once and prints the same line to stdout.

The dry run renders the five script parameters from the reviewed plan and the operator inputs and prints them with the script SHA256 and the expected lock version. It opens no client. The residual identifiers never appear in any receipt: the `residual_consumption_ids_json` parameter is shown as a count and the SHA256 of the compact sorted JSON array, which is the same digest the script receives as `residual_set_sha256`.

The preflight opens a client under the caller credentials, records `SESSION_USER()` in the same process immediately before the checks, then evaluates every assert that precedes the first write of the script as one read only SELECT over the same predicate, with the script parameters bound as query parameters. It then reads the v1 lock row and checks it against the phase: `pre-disable` requires state `ready` at exactly `--expected-v1-lock-version`, `post-disable` requires state `disabled` at exactly that version. The receipt (`execution_cutover_preflight_v1`) carries `phase`, `expected_v1_lock`, `observed_v1_lock` and every check with its name, the script refusal code it predicts, pass or fail and the digest of the query text; `failed_checks` collects the failing names. In `pre-disable` the state is `ready_for_disable` only when the lock check passes, `assert_04_execution_approval_v1_lock_not_disabled` fails and every other check passes; any other combination is `refused`. In `post-disable` the state is `ready` only when every check passes, otherwise `refused`. A refused preflight carries the first unexpected refusal code, emits it on stderr and exits 1. The three asserts after the first write (the active generation readback, `@@row_count` and the lock readback) read the transaction's own writes and have no read only form; the receipt lists them under `post_mutation_asserts` as not evaluated, and only the transaction can prove them.

The v1 disable is irreversible, and the cutover transaction refuses when any guard fails after the disable, which would leave the estate with neither v1 nor v2 authority. So the disable is issued only after a `pre-disable` preflight has reached `ready_for_disable` under the Ogilvy actor. Today the v1 lock is `ready` at version 469 (readiness report), so the pre-disable preflight runs with `--expected-v1-lock-version 469`; the disable moves the lock to `disabled` at 470, and the post-disable preflight and the apply run with `--expected-v1-lock-version 470`. The preflight and the dry run do not read the two receipt files, so their paths may name files the disable has not written yet.

The apply reads the v1 disable receipt and the inactivity receipt (both must parse as JSON objects and carry a non-empty `contract_version`, and the disable receipt `lock_version` must equal the expected value, else `execution_approval_lock_invalid`), then runs a `post-disable` preflight in the same process and the same command run, and calls the cutover transaction only when that preflight is `ready`. No file can stand in for the in-process preflight, and a `pre-disable` receipt is refused even at `ready_for_disable`. The apply receipt (`execution_cutover_apply_v1`) embeds the preflight receipt, the two receipt summaries (contract version and file SHA256), the rendered parameters and, on success, the activation row the script returns. A refusal, whether from the preflight or from the transaction, is written to the same receipt with its code and exits 1.

The `plan-v2` rendering no longer carries an IAM derivation. The reviewed IAM delta document is the single source for routine authorizations.
