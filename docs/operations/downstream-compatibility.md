# Downstream compatibility matrix

Five consumers read what the 42 engine writes to staging. This page records, for each one, the reader that is live today with its file and line, the exact staging fixture that proves the machine-consumed format, whether the consumer bridges to a new format or keeps parity with the old one, what it does when its input is stale or missing, and where the production boundary sits. The QA canary namespace (`client_scope_id = 'qa_canary'` in `trends_v2_staging_qa`, identity `intelligence-42-qa@ogilvy-trends-v2.iam.gserviceaccount.com`) is excluded by every reader below, and `ops/tests/test_downstream_compatibility.py` loads every fixture named here through its reader so a drift fails the tree.

Readers are cited as `path:line` followed by the symbol on that line. Fixtures are files in the tree. Nothing on this page sends anything: the PULSE render is an unsent artifact and the production send entry points (`engine/src/alerts/email_digest.py` `send_email_digest`, `engine/src/alerts/detector.py` `send_daily_digest`) are not imported by any 42 module.

## Notes

The 42 row and the PULSE row are the two machine-consumed formats frozen under the fixture package contract (`engine/src/contracts/open_intelligence_fixtures.py`), and the ops test loads that package and renders the PULSE line with the route link. The Looker and health rows are validated by parsing the named SQL and YAML files. The daily summary row has no frozen fixture file; its formats are held by the two engine unit modules `test_daily_summary_prompt.py` and `test_generate_daily_summary.py`, which the engine suite runs.

## Recurring semantic QA

`engine/scripts/staging/run_42_semantic_canaries.py` proves seven cases through the ordinary readiness and claim semantics path and, with `--apply`, appends one row per case to `canary_results_v2` in `trends_v2_staging_qa`, the QA table the migration creates with a 90 day partition expiry. It never writes `trends_v2_staging` and never runs the persistence canary's cleanup. Every result carries `corpus_sha256`, a digest of the fixture rows for its date.

A failed run prints its result, writes one structured `severity: ERROR` line with `message: qa_semantic_canary_failed` and the failed cases to stderr, and exits 1. That line is what a log based alert matches. `--drill-break CASE` replaces one case's expectation with a state no engine path produces, so the operator can prove the alarm fires; its appended row carries `error_code = qa_drill_break`, and a real mismatch carries `semantic_expectation_mismatch`. Rerunning the same date without the flag must pass with the same `corpus_sha256`, which proves the corpus was unchanged.

`ops/tests/test_qa_canary_isolation.py` scans every fixture directory for the QA scope, the canary name and every synthetic identifier the runner can produce for 2026 and 2027, checks that no ordinary reader names the QA dataset, and checks that every view over scoped rows excludes `qa_canary`.

Not yet native: the QA service account is absent from the native listing, and no Cloud Run job, scheduler row or log based alert exists for this runner. Those need a reviewed resource and IAM amendment before the recurring schedule can start.
