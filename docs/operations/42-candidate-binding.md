# Candidate binding

`ops/certification/bind_candidate.py` writes one receipt that names the exact staging candidate a tester or assessor is looking at and says which native readback proved each part of it. It serves U06 (bind the frozen candidate before any frontend certification capture) and E04 (verify the final candidate bindings before the programme can close). It makes no network call. Every native value it binds comes from a receipt an existing tool already wrote on the owner's machine, so running it is a Tier 1 read.

## What it binds

| Subject | Proved by | Bound value |
|---|---|---|
| `verify_receipt` | `release.py verify` receipt with `release_index` state `verified`, the same plan and index bytes, every index reference read, taken within the freshness window | check time, index digest |
| `repository_commit` | index commit read against the build that pushed the app image | repository, commit |
| `trees` | pinned engine, app and ops inventories and contracts hashed by verify | tree, manifest and contract digests |
| `images` | registry manifests and build receipts read by verify | app and engine image digests, both builds |
| `service_revision` | verify revision readback | revision name, image, service account |
| `traffic` | verify service traffic readback | 100% to the revision under its tag, tester URL |
| `queue` | verify queue readback; a running queue also needs a `running_verified` resume receipt for the same binding, whose resume plan names the apply result verify reconciled, run after that route and before the verify read | queue state |
| `policy_deployment` | policy and deployment objects hashed and the ledger active binding read by verify | policy digest, deployment digest (ledger generation kept as evidence only) |
| `source_binding` | pinned source binding and authority object copies hashed by verify | evidence mode, source binding locator and digest, authority object digests |
| `served_assets` | each asset fetched from the tagged revision and hashed by verify | asset origin, asset digests |
| `design_package` | a clean checkout at the index commit whose app tree inventory equals the index app tree; the vendored archive equals its pinned digest and names this version | package name, version, contract version, archive digest |
| `collection` | the owner's `read_ingest_run.py` receipt of one ingest execution, a real read (not `--dry-run`) whose state is `verified`, taken with `--source-sha` and `--image-uri` set to the source commit and engine image the ingest execution ran, so the daily stage's admission covered the build. The binder runs the tool's own checks again over what the readback recorded: the receipt's canonical text must hash to the digest the warehouse computed, the pinned policy and profile, the build, the start day and the daily stage's admission must hold, and the raw groups must be whole numbers inside the run's window that sum to the receipt's count and cover all three markets. The receipt and the rows must be recorded no later than the binding time | execution, run id, cutoff, receipt digest, policy, profile, source commit and image, collected markets, raw row count; the record time and the latest collection time per market are evidence |
| `captures` | the owner's unedited capture registry readback, run through the registry's own selection (`explain_capture_selection`) at the binding time for each required profile: the scope, `succeeded`, available, not expired. When `collection` is bound, the daily capture of its cutoff under its source policy is always required, named by the same function the daily capture stage registers it under (`staging-<cutoff>-<first 16 hex of the policy digest>`), its full policy digest must equal the collection's, and its `source_digest` must be the digest of the daily ledger copy of the bound receipt under `--collection-attempt-id`; profiles named with `--capture-profile` are required as well. The latest eligible capture of each required profile is bound and every entry's diagnostic is kept as evidence. Other profiles in the readback (an expired earlier day, another scope) are diagnostics only. A required profile with nothing eligible, a missing or malformed collection attempt id, a collection capture under another full policy or of another receipt or attempt, any entry that fails the registry grammar, or a profile binding conflict leaves the subject unproven | profile, operation, result, generation, content digest, source digest, markets, dates |
| `released_runs` | the owner's quality release record readback, one row per run | run id, run receipt digest, release time |

The ReleaseIndex is not validated twice. The binder runs the same closed index grammar (`validate_release_index_shape`) and then relies on the verify receipt's record that `validate_release_index` resolved every reference against native bytes.

The collection's own capture is tied to the exact receipt and collect attempt: the daily collect stage records a ledger copy of the admitted ingest receipt (authority kind dropped, execution id replaced by its own attempt id) and the capture runner records that copy's digest as `source_digest`. The binder rebuilds the copy from the bound receipt and `--collection-attempt-id` with the same engine functions (`daily_ledger_copy` and `receipt_source_digest` in `ingest_receipts.py`) and requires the digests to match, so a capture of a retried execution, or of another attempt, leaves `captures` unproven. Captures and released runs prove the identity and completion of what the candidate answers from. They do not prove that a given answer was served from them; answer provenance is proved by the question receipts.

## States

The receipt state is `bound` only when every subject is bound; `candidate_id` is then the canonical digest of the bound identity values. Values that move with ordinary use, such as the ledger generation that every admitted question advances and the time the queue was resumed, are recorded as evidence beside the value and are not part of the identity. Times in the identity are normalised to UTC. The queue state is part of the identity, so resuming the queue after binding gives a new candidate id; bind again after the resume. A subject whose input is missing or whose check fails is `unproven` with a reason, never dropped, and the command exits 1. Malformed input files refuse with a named error and write nothing. A verify receipt older than `--max-age-minutes` (default 60) or dated after the binding time binds nothing, because the other subjects are read out of it.

Drift the verify receipt records on the service, revision, traffic, queue or ledger leaves that subject unproven. Any other drift, an unproven apply operation for example, voids the verify receipt. After `release.py resume`, verify reports `queue_not_paused`; that one queue drift is accepted only with the resume receipt and its plan.

A later change invalidates only the certification receipts bound to the subjects it touched. `compare` names those subjects; a subject unproven in either receipt counts as changed.

## Commands

Run from a fresh detached worktree at the release commit, which is also the clean checkout the design package is read from; any other commit leaves the design package unproven.

```bash
set -C
STAMP=$(date -u +%Y%m%dT%H%M%SZ)
R=~/dev/42-receipts
py -3.13 ops/certification/bind_candidate.py bind --release-index $R/release-index.json --plan $R/release-plan.json --verify $R/release-verified-$STAMP.json --resume $R/resume-result.json --resume-plan $R/resume-plan.json --repo . --captures $R/capture-entries-$STAMP.json --capture-scope $CAPTURE_SCOPE --release-records $R/release-records-$STAMP.json --ingest-readback $R/ingest-readback-$INGEST_STAMP.json --collection-attempt-id $COLLECTION_ATTEMPT --max-age-minutes 60 --output $R/candidate-binding-$STAMP.json
py -3.13 ops/certification/bind_candidate.py guide --binding $R/candidate-binding-$STAMP.json --output $R/candidate-guide-section-$STAMP.md
py -3.13 ops/certification/bind_candidate.py compare --previous $R/candidate-binding-$EARLIER.json --current $R/candidate-binding-$STAMP.json
```

The verify receipt must be a fresh `release.py verify` run with `--release-index`, taken just before binding. Omit `--resume` and `--resume-plan` while the queue is paused. `$CAPTURE_SCOPE` is the `client_scope_id` the brief's capture step reads natively from the approved daily capture plan and passes through unchanged (the configured default client scope when the plan names none), never taken from the entries being checked; no scope is pinned in the code, so without it `captures` stays unproven. The collection's own capture is required without any `--capture-profile`. Add `--capture-profile` once for each further profile the candidate answers from, named by its approved profile and never taken from the entries being checked. Without a bound collection and without `--capture-profile`, `captures` stays unproven. `--ingest-readback` is the receipt `engine/scripts/staging/read_ingest_run.py` wrote for the ingest execution the candidate's data was collected by; without it `collection` stays unproven. `$INGEST_STAMP` is the stamp of that readback's own run, which is usually earlier than `$STAMP`. `$COLLECTION_ATTEMPT` is read natively by the owner from the collection ledger in bucket `ogilvy-trends-v2-execution-approvals-staging`: in the day index object `42/daily/collection/days/<cutoff plus one day>.json`, the `execution_id` of the one entry whose `run_id` is the collection's run id (its receipt object is `42/daily/collection/receipts/<that id>.json`). It is never taken from the capture entries being checked. Without it, a bound collection leaves `captures` unproven. Every identity value of `collection` comes from the receipt its digest covers. The binder cannot tell an edit that also redid both digests from a real read, so the bound receipt digest is part of the identity and an assessor can compare it with `collection_receipts` directly. No digest covers the record time or the raw groups (their markets, sources, counts and times). The groups are held to the receipt only through their sum and the markets they cover, their times to the run's window, and the record and group times to the binding time; the times are kept as evidence that only a read of the warehouse proves. The binder does not check the readback's query log, byte totals or byte cap, which describe how the read ran rather than what it found. `--captures` is a JSON list of capture registry entries and `--release-records` a JSON list of rows from `open_intelligence_quality_release_records_v2`, both read by the owner and saved unedited.

## Guide section

`guide` renders the candidate section of Albert's staging testing guide from the binding receipt alone: the tester URL, revision, commit and design package version; source dates from the bound collection, captures and released runs; the mandatory journeys to try; known limits (markets no capture covers, and every unproven subject with its reason); and a short feedback form. An unbound receipt renders as not ready for testing and lists what failed. The section is written to the receipts folder for each candidate; it is merged into `docs/operations/42-staging-testing-guide.md` only for the frozen candidate Albert is asked to test, and the journeys it lists are what to test, not results.
