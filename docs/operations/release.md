# Release lifecycle

`ops/deploy/release.py` makes deploy, readback, resume and rollback one tested lifecycle. Every native client (Cloud Run, Cloud Tasks, the evidence bucket, a byte reader and a clock) is injected through an adapter factory named on the command line, so the controller itself never runs Git, gcloud, HTTP or an SDK call. The dated 20260909 prepare, resume and activation scripts were ported first; their field invariants, queue audience, worker path and timeout policy are module constants and `ops/tests/test_foundation_release.py` pins them to the dated values.

Every command loads `ops/deploy/resource_manifest.json` through `resource_guard.load_resource_manifest` with the independently approved digest `33ed5155608920fddc36e199e77a3082b381b65c3dcd0d803f201811571f1e09` and calls `resource_guard.assert_allowed` before each guarded read and before every mutating adapter call. Output files are write-once: every command, `plan` included, refuses an existing path with `output_exists` before any native read. Refusals print one JSON line with `state`, `error` and `output` and exit 1; only a proven result exits 0.

## Adapter boundary

`--adapter PATH.py:factory` names a Python file (or importable module) and a factory. The factory receives the opaque `--adapter-state` value and returns a dict with `run`, `tasks`, `objects`, `bytes` and `clock`. The reference double is `ops/tests/fixtures/release_fake_adapter.py`; a native adapter for the conductor must expose the same methods: `run.get_service`, `run.get_revision`, `run.deploy_revision`, `run.update_traffic`, `run.read_operation`, `tasks.get_queue`, `tasks.list_tasks`, `tasks.pause`, `tasks.resume`, `objects.read`, `objects.create` (generation conditional), `bytes.read`, `bytes.reader` and `clock.now`, `clock.monotonic`, `clock.sleep`. The clock is the only time source, which is how the tests drive stale, future and elapsed cases deterministically. `bytes.read(reference)` resolves a reference that carries its own locator: `object:gs://listening-post-staging-cache/<name>#<generation>` from the evidence bucket, and `source:<https url>` by an anonymous GET, which the pricing renewal uses; the native adapter sends a `source:` request only to the host of the policy module's pricing source and never with a credential. `bytes.reader(index, asset_origin=...)` binds the reader to one release index and to the tagged revision URL and returns the callable `validate_release_index` consumes, described under the release index below.

| `verify` | `--plan`, `--result`, `--output`, `--release-index`, `--adapter`, `--adapter-state`, `--resources`, `--resources-sha256`, `--deadline-seconds`, `--poll-seconds` | read-only, reconciles a recorded unproven operation by identity | service, queue and bucket `read` |
| `resume` | `--plan`, `--output`, `--adapter`, `--adapter-state`, `--resources`, `--resources-sha256`, `--deadline-seconds`, `--poll-seconds` | resumes the paused queue | queue `write` before `resume` |

`--resources` defaults to the manifest beside the script and `--resources-sha256` to the approved digest. `--deadline-seconds` (default 600) and `--poll-seconds` (default 5) bound `wait_operation`; a deadline yields `unproven`, never success and never a resubmission.

A native run names the adapter in the tree, `--adapter ops/deploy/release_native_adapter.py:factory --adapter-state owner-gcloud` (or `adc` for application default credentials), which drives Cloud Run v2, Cloud Tasks v2 and the storage JSON API through REST requests with explicit bodies (`services.patch` with `updateMask=template` for the no-traffic revision and `updateMask=traffic` for the route, `operations.wait` for readback, `objects.insert` with `ifGenerationMatch`) and records every request and response on the adapter with the bearer token never written. The transport follows no redirect at all and refuses every 3xx by name with `redirect_refused`, naming the status and both origins. Two harms sit behind one redirect. Python's redirect handler copies the request headers onto the redirected request, stripping only the content headers, so one `Location` hands the owner bearer token to whatever host it names; and 301, 302 and 303 turn a POST into a GET with the body dropped, so a `:pause` or a `:wait` that never ran would come back 200 from the redirect target while the record still named the original URL and the status check counted a call that did not happen as a success. Following with the credential stripped closes neither completely, because the redirecting host would still choose which server answers a release request, so a same host redirect is refused too. A 200 whose body is not JSON refuses `response_not_json` after the response is recorded, so an error page served with a 200 is not counted as a successful call, and a transport result with no `status` refuses `transport_response_invalid` instead of raising a `KeyError`. Only 200 is accepted: every call here is documented to answer 200, and an unexpected 2xx on a write is now recorded as unproven with the effect to reconcile against, so the strictness costs no receipt. The plan's idempotency key now travels on the wire as the `X-Idempotency-Key` header on the two mutating Cloud Run calls that carry one, beside the copy kept on the record; Cloud Run v2 offers no server side idempotent replay, so the key identifies the request end to end and the real protection against a repeat remains the before state digest and the write once receipt. The activation receipt that `plan` verifies is produced by `ops/deploy/activate_question_deployment.py --build $RECEIPTS/build.json --lp-commit <hex40> --engine-commit <hex40> --engine-bundle-digest <hex64> --gate-sha256 <hex64> --policy-digest <hex64> --revision-name listening-post-staging-q-<date>-<engine7> --sdk-version 2.20.0 --adapter $ADAPTER --adapter-state $STATE --output $RECEIPTS/activation.json`, which pauses the queue and reads it back paused and empty, creates the binding object on generation 0, refreshes the ledger by compare and swap on the generation it read, reads the ledger back and writes the receipt from those readbacks, each step behind `assert_allowed` on the exact resource. Its `--dry-run` renders every mutation request and writes nothing; its refusals are `queue_not_empty`, `queue_not_paused`, `binding_conflict`, `ledger_binding_conflict` and `ledger_moved`, none retried, and a rerun after success reuses the binding object and skips the ledger write.

A staging release runs as three commands:

```powershell
& $PY ops/deploy/release.py plan --activation $RECEIPTS/activation.json --authority $RECEIPTS/release-authority.json --adapter $ADAPTER --adapter-state $STATE --output $RECEIPTS/release-plan.json

& $PY ops/deploy/release.py verify --plan $RECEIPTS/release-plan.json --result $RECEIPTS/release-result.json --release-index $RECEIPTS/release-index.json --adapter $ADAPTER --adapter-state $STATE --output $RECEIPTS/release-verified.json
```

## Plan

`plan` verifies the activation receipt exactly as the dated verifier did (activation state, binding and policy digests, project, region, service, identity, revision prefix, forty and sixty four character hashes, reviewed inputs, the 240 second deadline, a paused queue, a successful build with one image whose name is the approved registry image and a successful boundary gate step naming the gate digest). It loads the authority object, which must carry `42_release_authority_v1`, purpose `release`, the approved manifest digest and a window that contains the adapter clock; `authority_expired` refuses before any native read. It then captures the before state (redacted service, queue, complete task enumeration, ledger generation and digest), requires a paused empty queue and a ledger equal to the activation's `control_after` with the new binding active, and writes the plan. The plan holds the manifest digest, the immutable before state and its digest, the expected revision, image, source commit, bundle digest, policy digest, deployment digest, tag and worker URL, the exact changes (`deploy_revision` with the full template when the revision does not exist yet, then `route_traffic`), and an `idempotency_key` equal to the SHA256 of the canonical plan bytes without the key. Any later edit to the plan changes the key and `apply` refuses with `idempotency_key_mismatch`.

Environment entries are compared by name and plain value against the ported expected map. The template also carries the three entries the serving revision holds beyond that map: `CACHE_TTL` as the pinned plain value `86400`, a twelfth allowlisted key so the before state diffs against the deploy template; `GENERAL_QUESTION_BRIDGE_READS` as the fixed plain value `enabled`, a thirteenth allowlisted key and no operator input, which turns on the worker's reads of pinned bridge captures and does nothing while no bridge entry is pinned; and `UI_PASSCODE` as a secret reference by secret name and version alias (`ui-passcode-staging`, `latest`), compared by name and reference equality in `verify_service` and `verify_revision`, carried by the plan's `deploy_revision` template as the deploy input, and recorded by every redacted before, after and native block only as `source: secret`, never as the reference or a value. `verify_service` and `verify_revision` require the bridge reads switch at exactly `enabled` on every revision this lifecycle deploys or renews, so its absence is drift. A rollback target, and the routed revision a resume after rollback reads, may predate the switch and carry none; any value one does carry must still be `enabled`. A resume after a forward release gets no such allowance: a routed revision without the switch refuses `revision_mismatch`. Receipts copy plain values only for the eleven allowlisted keys of that map; any other plain valued entry is recorded as its name plus a keyed SHA256 of the value, and a secret sourced entry as its name plus `source: secret`. No receipt copies a secret reference, an operator added value or the value itself; `test_receipts_never_carry_plain_secret_values` proves a synthetic secret never reaches the plan, apply or verify bytes.

## Apply

`apply` reloads the plan, checks the key, the manifest digest and the authority window, reserves the write-once receipt, recaptures the before state and refuses with `before_state_changed` if its canonical digest differs from the plan. It then executes the changes in order. Each `deploy_revision` and `update_traffic` call is preceded by `assert_allowed(service, "deploy")` and carries the plan's idempotency key. Each returned operation is read back with `wait_operation` using the adapter clock. A `failed` operation stops immediately; an `unproven` operation writes `unproven_requires_reconciliation` and exits 1 with the saved operation identity in the receipt. The retry path is `verify`, which reconciles that identity; running `apply` again refuses because the receipt exists. When the response to the write itself is lost, there is no operation name to save and the server may still have applied the write, so the receipt records the change as unproven with a null operation, the transport error and a `reconcile_by` block naming the effect to settle against (the revision for a deploy, the routed traffic for a route). `verify` reconciles such a record by reading that effect back rather than by operation name: a revision that exists and passes the revision check settles as `succeeded`, a traffic readback that is terminal on the bound revision at 100% under the expected tag settles as `succeeded`, and everything else stays unproven and lands in the drift list. Each branch settles its own record, so a receipt whose `reconcile_by` names a kind this build does not read settles nothing: it stays unproven with `reconcile_target_unknown` having made no native call at all, and a `reconcile_by` that is not the shape the code reads refuses `reconcile_target_malformed` the same way. A revision or service the readback cannot find refuses `revision_unavailable` or `service_unavailable`; a revision that is present but bound to another identity or never Ready refuses `revision_mismatch` or `revision_not_ready`; traffic that never moved refuses `route_not_terminal`. The reconcile read travels the same transport that already lost one reply, so it can lose its own: a native, URL, HTTP or socket failure is recorded on the still unproven record as `reconcile_read_failed: <type>: <message>` rather than ending verify with nothing written for the operation that needed settling. The adapter's credential and configuration refusals and any programming error are deliberately not recorded there; they end the command loudly instead. Nothing is ever resubmitted. After routing, the service template, revision, traffic and traffic statuses must equal the expected targets, the queue must still be paused and the ledger generation unchanged; the receipt state is then `traffic_verified_100_queue_paused`, the dated name.

## Verify

`verify` rereads the service, revision, queue and ledger, reconciles any recorded unproven operation by its saved name, and lists every drift item (service, revision, traffic, queue, ledger binding, operation state). With `--release-index` it validates the shared `ReleaseIndex` (schema `42_staging_release_v3`, produced by `ops/deploy/release_index.py`, see the release index section) against actual bytes through the adapter byte reader bound to that index and to the plan's tagged revision URL, and binds the index to the plan (app image, policy digest, deployment digest, manifest digest and source commit must match) before recording `release_index_sha256`. A hex value without readable bytes refuses with `release_index_bytes_unavailable`; bytes with a different digest refuse with `release_index_digest_mismatch`. Every `raw_authority_objects` entry and the `source_binding` must name the approved evidence bucket `listening-post-staging-cache`; any other bucket refuses with `release_index_invalid` in the grammar, before a byte reader sees the URI, so a credential is never spent on an object the resource manifest does not cover. The bucket is compared for equality after the URI is split, not matched inside a pattern, because a pattern that lost its separator would accept a bucket whose name merely extends the approved one and a pattern matched by search would accept a foreign bucket carrying the approved name later in the string. The grammar is not the only barrier: the native byte reader checks the bucket itself and raises `object_bucket_not_approved` before it builds a request, so a reference reaching it by any other route still spends no credential. An index that does not resolve is drift like every other failed check: the receipt still lands, its `release_index` block records the schema version, the index digest, the references actually read in order and the counts behind them, and `state` there is `unproven` while `drift` names `release_index` with the refusal. Recording what was read is what distinguishes a run that checked fourteen references from one that checked thirteen because the index listed no served asset. The three services the index check reads beyond the service, the queue and the bucket are guarded first, and a guard refusal is not drift: it stops the run with no receipt, because an unauthorised read is not a fact about the release. Any drift yields state `unproven` and exit 1. No future revision is guessed into the index; verify only certifies what it read.

## Release index

The shared `ReleaseIndex` is schema `42_staging_release_v3`. It carries the v1 fields (repository, commit, the three tree inventory digests, the two image references by digest, the resource manifest digest, the policy and deployment digests, `contract_digests`, generation pinned `raw_authority_objects`, `evidence_mode`, `source_binding` and `served_assets`) with three additions and one change of meaning.

`app_build` and `engine_build` name the Cloud Build runs that pushed the two images, as `projects/<project or project number>/locations/us-central1/builds/<id>`; the project is pinned by the pattern, so a name from another project is refused by the grammar rather than by a check the reader runs after the request has gone out. `evidence_objects` maps each reference whose bytes the producer pins to an object binding `{uri, generation, sha256}`, and `raw_authority_objects` entries gain a `name`, unique within the index, so each has a pinned copy that can be addressed. The change of meaning is that `raw_authority_objects` and `source_binding` are now provenance: they record where those bytes came from, and the validator does not fetch them.

That change is the point of v3. An object at a digest named path cannot be superseded with different bytes, because the name is the content: the policy at `general-questions/policies/<policy_digest>/policy.json` and the binding at `general-questions/deployments/<deployment_digest>/binding.json` are still read live, and reading them live is better evidence than a copy, since the producer did not write them. The ledger is the opposite case. It lives at one fixed name, every activation and every pricing renewal writes it, the bucket keeps no versions, and a superseded generation is then unreadable: the generation the first published index pinned as its source binding already returns 404, and the generation it pinned as the activation ledger reads only because it happens to be current, so the next renewal would make that index unverifiable too. So the rule is that any reference which has to resolve later may not point at an object another writer can supersede, and the pre activation ledger, the activation ledger write and the deployment binding object are pinned under the release prefix instead.

The pinned set, which is exactly what `evidence_objects` must contain, is the three tree inventories, the resource manifest, one entry per reviewed contract as `contract:<name>`, one entry per raw authority object as `authority:<name>`, and `source_binding`. Each binding's URI must be `gs://listening-post-staging-cache/open-intelligence/v2/staging/releases/<commit>/<reference>`, with the first colon in the reference becoming a slash, and each binding's `sha256` must repeat the digest the index already records for that reference: the tree or manifest digest, the contract digest, the authority record's digest, or the source binding's digest. Contract and authority names are limited to letters, digits, dot, underscore and hyphen, since they become object names. Only v3 is accepted: v1 names no build, so nothing outside the index attests the commit or either image, and neither v1 nor v2 pins the authority objects or the source binding, so both expect a read that the next write destroys.

`validate_release_index` reads every reference through the bound reader and requires the bytes' SHA256 to equal the recorded digest (the `commit` bytes must equal the commit text). Each reference resolves to the most native source that exists for it, and the values the producer computed prove only that the checkout and the uploaded evidence agree, which is why the rest resolve to sources the producer did not write:

| Reference | Native source | Request |
|---|---|---|
| `commit` | the revision Cloud Build recorded for `app_build`, accepted only when that build is in the project, succeeded and pushed the `app_image` digest; otherwise `release_index_build_project_mismatch`, `release_index_build_not_successful` or `release_index_build_image_mismatch` | `GET https://cloudbuild.googleapis.com/v1/<app_build>` with the bearer token |
| `engine_image`, `app_image` | the image manifest, whose SHA256 is the image digest, fetched only after the build receipt the index names for that image says it pushed exactly that digest, since a digest that hashes the manifest it was used to fetch proves only that the registry holds that manifest | `GET https://cloudbuild.googleapis.com/v1/<build>` then `GET https://us-central1-docker.pkg.dev/v2/ogilvy-trends-v2/intelligence-42/<image>/manifests/sha256:<digest>` with the OCI and Docker manifest media types in `Accept` |
| `policy`, `deployment` | the stored policy and binding objects, returned as the digest preimage: the object minus the field naming its own digest. The stored bytes must themselves be the canonical bytes the digest was minted over, so a pretty printed, escape rewritten, whitespace padded or duplicate key object is not accepted as the object the digest names | storage metadata then media at the generation the metadata named |
| `asset:<path>` | what the tagged revision serves for that path, fetched without any credential; a path that is absolute, has a scheme or a dot segment is unavailable | `GET https://<tag>---listening-post-staging-fibxg5ynpq-uc.a.run.app/<path>` |
| every key of `evidence_objects` | the pinned object the binding names | storage metadata then media |

Served assets are the one path still unproven against the deployed service: the staging revision is private, and nothing here has yet fetched an asset from it anonymously, so an index that lists a served asset may fail against the real revision even though the fixture proves the mechanism. The release now on staging lists none.

`ops/deploy/release_index.py` produces the index in two commands. `build` runs offline: it refuses an existing `--output`, requires the checkout at `--repo` to have `HEAD` equal to `--commit` (`checkout_not_at_commit`) with no modified tracked file (`checkout_dirty`), and reads every tracked blob at that commit from the git object store, so the inventories describe the commit and not the working copy's line endings. `engine_tree` inventories `engine/`, `app_tree` inventories `app/`, and `ops_tree` inventories `ops/`, `infra/` and `cloudbuild.app.publish.yaml`; each is `sha256  path` per file, sorted by path, one line each. The resource manifest payload is `ops/deploy/resource_manifest.json` at the commit and must hash to the approved digest. Each `--contract NAME=PATH` names a reviewed contract file at the commit.

The receipts supply everything the checkout cannot. `--app-build` and `--engine-build` are the Cloud Build receipts (`gcloud builds describe --format=json`); each must have succeeded, name the project and push exactly one image of the expected name, the app build must have built `--commit`, and the two names become `app_build` and `engine_build`. `--activation` is the activation receipt, verified as `plan` verifies it; its binding must name `--commit` and the app build's image digest. Its `chain` supplies the two `raw_authority_objects`, `deployment_binding` and `activation_ledger`, with the generation and SHA256 the activation recorded, and the bytes behind both are rebuilt locally from the receipt (the binding value and the control ledger, in canonical form) and must hash to those recorded digests, so `build` still makes no request. `--release-result` must be the apply receipt in state `traffic_verified_100_queue_paused` for that binding. `--ledger-copy` is the ledger as read before the activation wrote it: its bytes must be canonical, and applying the activation to them, adding the new binding and swapping the active digest, must reproduce the activation's control ledger exactly, which is what ties an operator supplied file to a digest the activation receipt already recorded. Its SHA256 and the activation's `ledger_generation_before` become `source_binding`. `--served-assets` is an optional JSON map from served asset path to SHA256; the producer cannot compute served assets from the checkout, so this is the one field recorded from operator input, and `verify` checks it against what the tagged revision serves. `--evidence-mode` is `retained_baseline` or `daily_capture`. The output directory holds `draft.json`, the index without `evidence_objects` plus each payload's file, SHA256 and object name, and the payload files under `evidence/`.

`publish` loads the draft, refuses an existing `--output`, and for each payload in reference order calls `assert_allowed` on the bucket for `write` and then `objects.create` with `ifGenerationMatch=0`, reads the object back at the generation it received and requires the bytes to match (`evidence_readback_mismatch`). An object that already exists with identical bytes is reused at its generation; one with different bytes refuses `evidence_object_conflict`. It then writes the final index with `evidence_objects` filled in, after running the grammar over it. `publish` makes no read or write outside the bucket.

## Resume

Queue resume has three separate paths chosen at plan time with `--kind resume --mode empty|recovery|drain-expired` and a `--route` receipt from a verified apply. `empty` refuses any pending request flag (`pending_flags_forbidden`). `recovery` and `drain-expired` require `--pending-request`, `--parent-request` and `--anchor-request` together (`pending_request_required`). The plan encodes the mode and the identifiers. Both the plan and the later `resume` command run the ported preflight: at least 125 seconds since the route finished (`drain_not_elapsed`), the service template equal to the binding with exactly one traffic status at 100% on the expected revision and tag (`route_not_terminal`), a paused queue, a complete task enumeration within twenty pages and one thousand tasks (`task_enumeration_incomplete`), every task targeting the tag worker URL, the binding identity and the canonical audience (`task_audience_mismatch`), and a ledger whose active binding and policy match (`ledger_incompatible`). Recovery also checks the single pending row (digests, reservation, no executed calls or queries, at least 190 seconds remaining at preflight and 180 at the final check), the single task (name, dispatch count, the 270 second dispatch deadline, the invocation body), the intake object at its recorded generation and the parent context capsule. Expired drain requires the remaining time to be at or below zero (`request_not_expired`) and, when a result pointer exists, a terminal result in state `unavailable` or `held` whose digest and bindings match. The ledger must equal the activation `control_after` plus the pending row (`ledger_changed`). Only then does `resume` call `assert_allowed(queue, "write")`, resume the queue and read it back; `running_verified` exits 0, anything else is `resume_unproven`.

```powershell
& $PY ops/deploy/release.py plan --kind resume --mode empty --route $RECEIPTS/release-result.json --activation $RECEIPTS/activation.json --authority $RECEIPTS/release-authority.json --adapter $ADAPTER --adapter-state $STATE --output $RECEIPTS/resume-plan.json
& $PY ops/deploy/release.py resume --plan $RECEIPTS/resume-plan.json --adapter $ADAPTER --adapter-state $STATE --output $RECEIPTS/resume-result.json
```

## Rollback

`rollback-plan` needs an authority with purpose `rollback` and a `--target-revision`. It captures the before state and, when the queue is not paused, records an explicit `pause_queue` step as the first change so `rollback-apply` pauses the queue through the guarded adapter before anything else; without that planned step `rollback-apply` refuses a running queue. It classifies every ledger request as completed, held, in flight, queued or expired unexecuted, and refuses `rollback_in_flight_request` while any request is executing. It reads the target revision itself, never the service template: the revision's container image, deployment digest and source commit must match the stored binding object for that digest, the binding must validate under the current deployment contract, its policy object must validate, its runtime fields (SDK version, worker path, audience, identity, service) must equal the active binding, and the revision must pass the ported revision check. A missing revision refuses `rollback_target_missing`; a binding that fails the contract refuses `rollback_incompatible_schema`. Every refusal after the before state is captured writes the receipt with `forward_recovery_plan`, which keeps the queue paused, lists every preserved request and points to the forward path.

`rollback-apply` recaptures the before state and refuses `before_state_changed` if the ledger generation, service, queue or tasks moved. Before it executes anything it checks the order of the plan's changes: they must be exactly an optional `pause_queue`, then `activate_binding`, then `route_traffic`, and any other sequence refuses `rollback_change_order_invalid` with nothing sent. The plan is sealed with a recomputable digest rather than a signature, so anyone who can write a plan can re-seal one; the order is therefore enforced at apply time and not trusted from the plan. The route step carries its own precondition as well, the counterpart of the service check the release path already makes before it routes: it rereads the ledger and requires the generation the activation wrote and the target's deployment digest still active, refusing `rollback_activation_unconfirmed` before any traffic moves. When the plan carries a pause step it pauses the queue first, reads the queue back as paused, rereads the ledger at the planned generation and classifies again. It then writes the ledger with `if_generation_match` equal to the planned generation, changing only `active_deployment_digest` and, where needed, appending the target binding; every request, result pointer, reservation and unknown debit is copied byte for byte and the ledger is never replaced by an older snapshot. A failed conditional write refuses `stale_ledger_generation`. It then routes the target revision through `update_traffic`, reads back terminal traffic, rereads the ledger and asserts the canonical request bytes and reserved total are unchanged, and reports `resume_eligibility`. The terminal receipt state is `rollback_verified_queue_paused`, and that receipt is the `--route` input for the resume plan. A route failure leaves `failed_or_unproven_requires_native_reconciliation` with the queue paused and a forward recovery plan whose `route` entry names the route operation, its readback state, the target revision and the activation generation. That entry is filled in before the traffic write goes out, so a dropped response or any other failure from that point on still emits a recovery plan carrying the route; when no operation name survived, the entry holds a null operation and state `unknown` and the plan tells the operator to read the service traffic back natively instead of naming an operation. A recovery plan that omitted the route would tell the operator to prepare a forward activation while the old revision was already serving traffic.

The rollback drill needs no manual queue pause. `rollback-plan` records the `pause_queue` step whenever the queue is not paused, and `rollback-apply` runs it first, reads the queue back and records the readback in `queue_paused`; a readback other than `PAUSED` refuses `queue_not_paused` before any ledger write, labelled `failed_or_unproven_requires_native_reconciliation` because a queue write was issued and the native queue state must be checked. An already paused queue plans no pause step and no pause call is made, so a queue paused earlier by hand or by an earlier attempt is left alone. Admissions have no pause of their own. The ledger control record is the closed field set the app validates (`contract_version`, `allowance_id`, `active_deployment_digest`, `bindings`, `requests`, `reserved_microusd`), and the app refuses a new request only when the active digest or the binding does not match its own, or when the request budget is spent. The plan therefore carries `admissions_pause` with state `unsupported_by_ledger_control` and the reason, the receipt copies it, and the controller writes no marker the app would reject as `control_invalid`. What closes admissions on the outgoing revision is the activation write itself: once `active_deployment_digest` names the target, the outgoing revision refuses new requests with `approval_required`, and the target revision admits only after traffic reaches it. A marker the app honours ahead of that write is an app contract change for the question lane, not for this controller. When the route fails after the ledger write, the ledger is not reversed: the receipt keeps `activation` and the route readback, and `forward_recovery_plan.route` names the operation, its state, the target revision and the activation generation. A repeated `rollback-apply` on the same plan refuses `before_state_changed` because the ledger generation moved, and a fresh `rollback-plan` for the same target refuses `rollback_target_already_active`, so the repair is native: keep the queue paused, reconcile the named operation, route the target revision again and read the traffic back. A concurrent ledger write between the plan's before state and the activation write refuses `stale_ledger_generation` with `activation.state` recorded as `failed` and no route attempted. `test_rollback_apply_never_pauses_an_already_paused_queue`, `test_rollback_apply_refuses_before_any_ledger_write_when_pause_reads_back_running`, `test_rollback_plan_records_admissions_pause_as_unsupported_by_ledger_control`, `test_repeated_rollback_apply_after_route_failure_refuses_and_names_the_route` and `test_rollback_ledger_compare_and_swap_refuses_a_concurrent_write` pin these paths against the local double. The native drill, including the route failure path with a real traffic readback, is still unproven.

Resume after a rollback takes the rollback receipt as `--route` with no `--activation` (passing one refuses `activation_forbidden`). The preflight verifies the routed revision through the traffic readback and the revision itself, never through the service template, so the template still naming the newer revision does not block it. The ledger must be byte identical to the receipt's `after.ledger` (generation and digest), and every task in the queue must target the routed binding's worker URL and audience; a task bound to the newer binding refuses `task_audience_mismatch` in every mode and the queue stays paused until that request is handled natively. A request bound to the compatible revision can only be drained after a rollback: the 125 second drain leaves fewer than the 190 seconds recovery requires, so `recovery` refuses `insufficient_remaining_time` and `drain-expired` resumes once the request has expired. `test_resume_after_rollback_accepts_rollback_receipt_despite_newer_template`, `test_resume_after_rollback_drains_expired_request_bound_to_compatible_revision` and `test_resume_after_rollback_refuses_requests_bound_to_the_newer_binding` cover the three paths.

```powershell
& $PY ops/deploy/release.py rollback-plan --target-revision listening-post-staging-q-old --authority $RECEIPTS/rollback-authority.json --adapter $ADAPTER --adapter-state $STATE --output $RECEIPTS/rollback-plan.json
& $PY ops/deploy/release.py rollback-apply --plan $RECEIPTS/rollback-plan.json --adapter $ADAPTER --adapter-state $STATE --output $RECEIPTS/rollback-result.json
```

## Readback

`ops/deploy/readback.py` exposes `wait_operation(reader, operation_name, *, deadline_seconds, poll_seconds, clock, sleep)`. The reader receives the operation name and a per read timeout bounded by the remaining budget and thirty seconds, and returns `operation`, `state` (`pending`, `succeeded`, `failed` or `unknown`) plus native evidence. Time is measured with the injected monotonic clock and includes the reader's own duration. A response naming a different operation raises `operation_identity_mismatch` after one read. Terminal failure returns after exactly one read. An exception that reports the read was never answered, meaning `OSError` and its subclasses other than an answered `HTTPError`, is recorded as `unknown` and polling continues. Every other exception ends the loop on that read, including a refusal by name and a native error carrying a status, because repeating an answered refusal spends the whole deadline replaying an authenticated request and still ends unproven. At the deadline the result is `unproven` with the last state, the last error and the full read trail; `resubmitted` is always false.

## Pricing renewal

`ops/deploy/refresh_question_policy.py` exposes `refresh_observed_policy(*, release_index, observation, grant, clients)`. The grant must carry `42_renewal_grant_v1`, purpose `pricing_renewal`, the approved manifest digest and a live window. The observation must name the approved pricing source, location `global`, tier `standard`, currency `USD`, the active model and rates as decimal strings; it must be no older than 24 hours and not in the future by the adapter clock. The controller fetches the source bytes through `bytes.read("source:<url>")`, requires their SHA256 to equal the observation and each observed rate to appear in the page text. It then reads the ledger and the active binding afresh, requires the release index app image and commit to match that binding (an older index cannot replace a newer active binding), builds the new policy with the engine's `build_question_policy` from the active approval contract so limits, stages, model, expiry and identifier are preserved, and applies `require_question_admission_policy`, which refuses `rate_above_reservation_bound`, `observation_stale`, `observation_future_dated` and `policy_expired`. An observation whose policy digest is already bound returns `already_activated` without another revision, object or reservation. Otherwise it writes the immutable policy and binding objects, deploys the same image with the new deployment digest and no traffic, verifies the revision, writes the ledger conditionally on the generation it read (`stale_ledger_generation` on a concurrent deployment, with the no-traffic revision recorded for reconciliation), routes traffic and rereads traffic and ledger. Requests and reservations are never touched. Once the ledger write has landed, any later failure or refusal (route failed or unproven, traffic unverified, ledger or requests changed) is labelled `ledger_moved_requires_native_reconciliation` rather than `refused`, and the receipt keeps the activation generation and every operation readback so the conductor can reconcile; an adapter exception before the ledger write returns `failed` and never escapes the controller.

The same module is the command line for a renewal, run as `python -m ops.deploy.refresh_question_policy` with one of three forms. `observe` writes the observation document: it fetches the approved pricing source through the adapter's byte reader as `source:<url>` (the URL is the module's own `PRICING_SOURCE`, never an argument, and the command accepts no `--source-url`), computes `source_sha256` from the bytes it fetched, stamps `observed_at` from the adapter clock, and takes `--model` and the two rates from the operator, typed from the page as the engine's six decimal strings (`0.750000`, `3.750000`); it then runs the controller's observation check and the rate proof on the document it is about to write, so a rate whose normalised form (`0.75`) is not in the page text refuses `observation_rate_not_evidenced`, a rate in any other format refuses `observation_rate_invalid`, a model outside the profile table refuses `observation_model_unknown`, and `--location`, `--service-tier` and `--currency` default to the approved scope and refuse `observation_scope_mismatch` when changed. The source is fetched exactly once per run. That is not a convenience: the vendor serves a different body on every request, measured at three consecutive reads two seconds apart returning 3282030, 3282000 and 3282037 bytes under three different digests, so a second fetch to check the first one's digest compares two different responses and refuses a correct observation. The tool never invents a price: the operator types what the page says and the controller proves it against the page bytes, at observe time and again at renew time. `renew` takes `--release-index`, `--observation` and `--grant`, each a local JSON path or an `object:gs://listening-post-staging-cache/<name>#<generation>` locator read through the adapter's byte reader (any other bucket or a locator without a generation refuses `<document>_locator_invalid`, an unreadable one `<document>_unreadable`), loads the approved manifest by the same path and digest `release.py` uses (`--resources`, `--resources-sha256`), builds the clients from the adapter factory and hands everything to `refresh_observed_policy`. The receipt at `--output` is written as `started` once the three documents are loaded, before the controller runs, and rewritten with exactly the receipt the library returns; the exit code is 0 only for `activated` and `already_activated`, 1 for `refused`, `failed` and `ledger_moved_requires_native_reconciliation`, with the controller's reason on stdout as `error`. The grant is written by hand and never by a tool: it is `42_renewal_grant_v1` with purpose `pricing_renewal`, the approved manifest digest, a window and a grantor. `renew --dry-run` loads the same three documents, runs the grant, observation, source, release index, ledger, active binding, active policy and admission checks exactly as `renew` does, then renders the five writes it would send (policy object, binding object, no traffic revision, ledger compare and swap on the generation it read, traffic route) with their resources, guard actions, object names, digests and, under the native adapter, the exact requests, and sends nothing. An existing `--output` refuses `output_exists` before any native call, for every form. Read the two values in the observation for what each is worth, because they are worth different things. `source_sha256` together with `source_object` is real evidence: `observe` writes the exact bytes it read into an immutable object in the approved bucket, named by the digest of those bytes so the name and the content cannot disagree, created with `ifGenerationMatch=0` behind `assert_allowed` on the bucket and read back after writing, and an existing object with that name is reused when its bytes are identical and refuses `immutable_object_conflict` when they are not. The observation carries the locator beside the digest, `renew` resolves it through the byte reader and recomputes the digest of what comes back, so the comparison is against bytes anyone can fetch and check at any later date. The rates are worth much less. They are evidenced by a substring search over roughly three megabytes of vendor marketing copy and nothing more, and that search accepts the rates swapped, the other model's rates, both rates a factor of ten out and the same number twice, because each of those digit strings occurs somewhere on the page; only digits that appear nowhere at all are refused. `test_the_rate_check_is_a_substring_search_and_the_test_says_what_that_means` asserts each of those acceptances rather than pretending otherwise. Parsing the vendor's table to do better would put a silently rotting parser behind a value the operator is already accountable for, so the authority for a rate remains the operator who read it off the page and typed it. Do not read the strength of the first value as covering the second. A failure to read the source is reported apart from a refusal to read it: `observation_source_not_approved` when the reference names anything but the approved source, `observation_source_unreadable` when the reader declines or returns nothing, and `observation_source_unavailable` when the fetch itself raises. `ops/tests/test_refresh_question_policy_cli.py` pins each of these paths against the local double, including that the dry run's rendered requests are the ones the real run then sends.

The contract for the observation is `42_pricing_observation_v2`, which is `v1` plus `source_object`. A `v1` document is still accepted so that work in flight is not stranded, and it takes the only path open to it, refetching the live page, which now answers a different body to every request and so refuses `observation_source_mismatch` in practice. Renewals should be run from a `v2` document, where the renewal makes no request to the vendor at all. Making `v2` mandatory means editing the renewal section of `ops/tests/test_foundation_release.py`, which this change does not own.

`observe` writes to the bucket, so it answers to the same grant the renewal does and it answers before anything is written: `--grant` is required, an expired or missing grant refuses with no native call made, and `--receipt` records what the run wrote and at what generation. `observe --dry-run` renders the object write and sends nothing. Every form of both commands writes a receipt carrying `42_renewal_receipt_v1`, the command, and the inputs it ran on, including the refusals, so a receipt can always be tied back to what produced it.

The dry run and the real run are one code path. The writes are suppressed at the single place they are issued rather than described by a second copy of the logic, so the request a dry run prints is built by the lines that send it. One field cannot work that way: the route carries the etag the service reports after the new revision exists, which no plan can know without deploying, so the dry run reports that etag as null and flags it `etag_unknown_until_deployed` rather than printing the value read before the deploy, which is not the value the run sends.

A rerun after a renewal that did not finish decides from both sides and never falls through to success. When a policy has multiple deployment bindings, all are checked before deciding: any binding that is both claimed and served returns `already_activated`, otherwise `renewal_policy_bound_to_retired_deployments` carries every binding and its claimed and serving flags in `split.bound_deployments`. All four combinations of what the ledger claims and what Cloud Run serves are named. Claimed and serving is `already_activated` and exit 0, and it is the only one of the four that exits 0, because in each of the other three the app refuses every question with `approval_required`. Claimed but not served is `ledger_ahead_of_served_revision_requires_native_reconciliation`. Served but not claimed is `served_revision_ahead_of_ledger_requires_native_reconciliation`. Neither is `renewal_bound_but_neither_active_nor_served`, which means the policy is bound to a deployment that nothing activates and nothing serves, so the renewal never took effect and rerunning will not make it take effect. Each of the three carries a `split` block naming the ledger's active digest, this renewal's digest, the revision and full traffic target expected, the revisions actually served and what a human has to do; the tool repairs none of them and does not retry. Serving is judged the way the acting path judges it, by requiring the service's traffic and its readback to equal the full target for the binding, not by asking whether the revision appears in the traffic list at all: a revision holding one percent is in that list while almost every question still goes elsewhere. A ledger write whose response is lost is distinguished from a refused precondition by reading the ledger back rather than by whether the call returned. Bytes matching what this run intended means the write landed, so the receipt records the activation, sets `ledger_moved` and reports `ledger_write_response_lost` under the reconciliation state; a generation that moved to something else is `stale_ledger_generation`; an unchanged generation is `ledger_write_failed`, and a ledger that cannot be read back at all is `ledger_write_outcome_unknown`. An observation is also refused when too little of its life remains for a renewal and then a question to run inside it, `observation_expires_before_a_question_can_run`, where the margin is two operation readbacks at `DEADLINE_SECONDS` plus the engine's own `QUESTION_DEADLINE_SECONDS`, twenty four minutes in total, taken from the values the code already spends rather than invented.

```powershell
& $PY -m ops.deploy.refresh_question_policy observe --model <model> --input-usd-per-million <rate> --output-usd-per-million <rate> --grant $RECEIPTS/renewal-grant.json --adapter $ADAPTER --adapter-state $STATE --receipt $RECEIPTS/observe-receipt.json --output $RECEIPTS/observation.json
& $PY -m ops.deploy.refresh_question_policy renew --dry-run --release-index $RECEIPTS/release-index.json --observation $RECEIPTS/observation.json --grant $RECEIPTS/renewal-grant.json --adapter $ADAPTER --adapter-state $STATE --output $RECEIPTS/renewal-dryrun.json
& $PY -m ops.deploy.refresh_question_policy renew --release-index $RECEIPTS/release-index.json --observation $RECEIPTS/observation.json --grant $RECEIPTS/renewal-grant.json --adapter $ADAPTER --adapter-state $STATE --output $RECEIPTS/renewal-receipt.json
```

The managed job `intelligence-42-price-policy-staging` runs a fourth form, `renew-unattended`, because `renew` cannot run unattended: its observation lives at most 24 hours and the rates in an observation are typed by a person. `renew-unattended` takes `--release-index` and `--grant`, each a local path, an `object:` locator pinned by generation, or, for its own fixed name under `open-intelligence/v2/staging/general-questions/renewal/`, a locator at generation `current` (see Why the job reads the current generation below), and makes its own observation. The grant is `42_unattended_renewal_grant_v1` with purpose `unattended_pricing_renewal`, written by hand and never by a tool, like the v1 grant: it carries the v1 fields plus `release_commit`, `model`, the two rates, `baseline_source_object` and `baseline_source_sha256`, the evidence object an attended `observe` pinned when those rates were read off the page. Its window is at most 92 days (`grant_window_too_long`). Neither grant is accepted by the other form (`grant_invalid`). In order, and before anything is fetched or written, the run checks the grant, the index shape and manifest digest, the index commit against the grant's `release_commit` (`unattended_release_commit_mismatch`), the index commit and image against the active binding, and that the active policy's model and rates are the grant's (`unattended_rates_not_proven`). `RENEWAL_INTERVAL` is enforced here: when the active pricing review is younger than the interval less `OBSERVATION_MARGIN` the run ends `not_due`, exit 0, having fetched and written nothing. It then reads the baseline bytes and recomputes their digest (`unattended_baseline_mismatch`), requires the baseline to be a whole page ending in its closing html tag (`unattended_source_truncated`), to carry at least one dollar amount (`unattended_source_changed`) and to carry each rate as a whole dollar amount, `$` followed by the rate's normalised form such as `$0.75` (`unattended_baseline_rate_not_priced`), all before the vendor is asked for anything. A rate printed without its dollar sign is not proof of a price, because the bare substring `0.75` occurs in `10.75`. It then fetches the live page once and requires it to be a whole page (`unattended_source_truncated`, so a body cut off after its last dollar amount is refused although its prices match), to carry each rate as a whole dollar amount (`observation_rate_not_evidenced`) and to carry the same ordered list of dollar amounts as the baseline (`unattended_source_changed`). The dollar list alone would let a changed row through wherever the old dollar amounts survive elsewhere on the page, so two more ordered lists must also be equal, both refusing `unattended_source_changed`: every decimal numeral with or without a dollar sign (`10.75` written bare or as `&#36;10.75`), and every unit token (`1M`, `1K`, `million`, `per token` and the like), so `/1M` becoming `/1K` under the same numbers is refused. What remains is stated rather than claimed away. The comparison is over tokens, not the vendor's table, so a page that keeps every dollar amount, decimal and unit token in the same order while changing what they label, a row renamed from one model to another for example, still passes; so does a price change expressed only in words or as a whole number without a dollar sign or unit, since whole numbers are not compared, the page's rotating markup being expected to carry whole numbers that differ on every request, which is unmeasured; a decimal inside a longer dotted run such as `1.2.3` is skipped rather than read; so is a decimal that ends a sentence, `0.38.` becoming `10.38.`, because the full stop after it reads as the start of a dotted run; the exponent of a number in scientific notation is not read, so `7.5e-7` becoming `7.5e-6` is not seen; and a unit written in a form outside that list is not seen. The full stop and exponent cases are pinned by `test_a_change_the_token_lists_cannot_see_keeps_the_grant_rates`, which asserts that each still activates and only at the grant's rates. Each of those still needs the rates to equal the grant, the active policy and a whole dollar amount on both pages, so none of them can move the price the job activates; they can only keep it at the last proven rate after the vendor has changed it, which is why the grant window is capped at 92 days. Only then does it pin the live bytes as an evidence object, build a `42_pricing_observation_v2` document on the grant's rates, and call the controller with `unattended=True`, which checks the unattended grant and refuses `unattended_rate_changed` if the observed rates are not the grant's and the active policy's at the acting point. It never reads a rate off the page, never writes a grant and never retries. The job's container is discarded when it exits, so its `--output` under `/tmp` is not the durable record: the stdout summary carries the whole receipt as `receipt` with `receipt_sha256` over its canonical bytes, and lifts `error`, `detail`, `mutations`, `activation`, `ledger_moved`, `ledger_readback_error` and `operations` to the top, so the job's log holds everything a reconciliation needs. The dollar list comparison is fail closed and unproven against the live page: if the vendor's rotating content moves dollar amounts between requests, every run refuses and the renewal stays attended. The vector in `infra/runtime/daily-staging.json` is `MANAGED_JOB_ARGS` with both generations reading `current`, the documents staged at their fixed names (see Staging the unattended documents below); the jobs plan is rendered by `ops/deploy/runtime_jobs.py plan` against an engine image built from a commit that carries this form. The scheduler stays paused. The run also reads `renewal/release-index.json`, `renewal/unattended-grant.json`, the baseline under `renewal/sources/`, the active binding under `deployments/` and the active policy under `policies/`, and creates the live evidence object under `renewal/sources/`, the new policy under `policies/` and the new binding under `deployments/`, all under `open-intelligence/v2/staging/general-questions/` in `listening-post-staging-cache`. A denied read, or a denied create under `renewal/sources/`, leaves nothing written; a denied create under `policies/` or `deployments/` leaves the content addressed objects created before it, the evidence object and then the policy, and nothing else.

## Staging the unattended documents

`refresh_question_policy stage-unattended` puts one of the two documents the managed job reads at its fixed name: `--release-index <file>` at `open-intelligence/v2/staging/general-questions/renewal/release-index.json`, or `--grant <file>` at `renewal/unattended-grant.json`, never both in one run, with `--output`, the adapter flags and optional `--dry-run`. The index goes first. It is checked for shape and manifest digest and against the live ledger and active binding (`release_index_image_mismatch`, `release_index_source_mismatch`). The grant goes after it, with a `granted_at` no earlier than the index object's creation time. Because a grant's whole text is shown before the go that stages the index, its `granted_at` may be a fixed time after all of that brief's writes: staging accepts a grant up to 24 hours before its `granted_at` (`grant_start_too_far` beyond that) and checks it as it will stand at `granted_at`, including the index time rule, and the job refuses `grant_not_yet_valid`, writing nothing, until `granted_at` has passed. Because a grant staged ahead leaves a gap before its `granted_at`, the job, when it reads the grant at `current` as the shipped vector does, also requires the index object to have been created no later than that grant object (`release_index_newer_than_grant`, or `grant_time_unavailable` when no creation time comes back with it), so an index restaged in that gap refuses. A grant given by pinned generation or local path is held to the `granted_at` rule only. Staging the grant reads the index at its name as it is now (`release_index_unreadable` when there is none), runs the job's own preflight against that index and the live ledger, active binding and active policy (grant contract and window, index shape and manifest digest, `unattended_release_commit_mismatch`, index image and commit against the active binding, `unattended_rates_not_proven`), refuses `release_index_newer_than_grant` when the index object was created after `granted_at`, and reads and hashes the baseline evidence object, so a document the job would refuse is never staged. Each document is written byte for byte as supplied, conditional on the generation it read at that name (`ifGenerationMatch` 0 when absent), read back at the generation it received (`staged_object_readback_mismatch` otherwise), and left alone when identical bytes are already there. The receipt names the generation, digest and `object:` locator of what it staged, and for a grant the generation, digest and creation time of the index it was checked against. It does not fetch the pricing page, touch the job or the scheduler, or write anything outside those two names. Every release restages the index and then a fresh grant naming the new commit; until both are done the job refuses.

### Why the job reads the current generation

The job's vector in `infra/runtime/daily-staging.json` reads both documents at generation `current`: `renew-unattended` reads each fixed name at the generation it has when the run starts and records that generation, its sha256 and the object's creation time in the receipt's `inputs`. `current` is accepted only by `renew-unattended`, only for `renewal/release-index.json` as the index and `renewal/unattended-grant.json` as the grant (`release_index_locator_invalid`, `grant_locator_invalid` otherwise). A locator whose generation reads `pending` still refuses before any native call.

This relaxes the earlier rule that the shipped vector reads `pending` and refuses before any native call until real generations are written in. That rule meant every release and every new grant needed a new job configuration and a job redeploy, which is a native step Albert would carry each time, and the point of the job is that he no longer renews by hand. Reading whatever is at a name is safe here only because a document found there can make the run refuse and cannot make it renew on anything the grant did not name. The grant is written by hand and names the release commit and the proven rates; the run refuses unless the grant is live and its `release_commit` equals the index commit and the active binding's commit; it refuses `release_index_newer_than_grant` when the index object was created after the grant's `granted_at`, so an index swapped in after the grant was written does not run even when it names the same commit, and `release_index_time_unavailable` when no creation time is read, which includes an index given by pinned generation or local path beside a grant read at `current`; and it records both objects' generations and digests, so what ran is known afterwards. A stale grant from an earlier release, an expired grant, an index swapped in later and a name with nothing at it each refuse with nothing written, as `ops/tests/test_refresh_question_policy_stage.py` shows. The two reads are separate, so a write landing between them is read as whichever pair the run saw, and that pair passes every check above or the run refuses.

## Question policy expiry

A question policy carries one of two expiries: the fixed `2026-09-30T23:59:59Z` or the extended `2026-12-31T23:59:59Z` (`EXTENDED_EXPIRES_AT` in `general_question_policy.py`). `validate_question_policy` accepts exactly those two, so a policy with the fixed expiry keeps validating on an image that knows the extended one. A renewal never changes the expiry: it builds the new policy with the active policy's own `expires_at`. The only path to the extended expiry is `refresh_question_policy extend-expiry`, which takes `--release-index`, `--grant`, `--output`, the adapter flags and `--dry-run`, exactly as `renew` does without an observation. The grant is written by hand: `42_policy_expiry_grant_v1`, purpose `policy_expiry_replacement`, the approved manifest digest, a window of at most eight hours, a grantor, `from_policy_digest` (the active policy it replaces), `to_expires_at` (the extended expiry, and nothing else is accepted) and `release_commit`, the released commit that carries this code, which must equal the release index commit (`expiry_release_commit_mismatch`) and so the active binding's. The command reads the ledger and the active binding afresh, requires the release index to name the active image and commit, reads the granted policy from the bucket, sets `expires_at` to the extended value, recomputes the digest and admits the result as a renewal would, so the last pricing review must still be inside its 24 hours (`observation_stale` otherwise) and every other field must be unchanged (`policy_scope_changed`). If the active binding no longer binds the granted policy it refuses `active_policy_moved` and writes nothing; a policy that already carries the extended expiry refuses `policy_already_extended`. It then activates through the same code a renewal uses: policy and binding objects, a no traffic revision on the same image, the ledger compare and swap on the generation it read, and the traffic route. A rerun after it has landed returns `already_activated`. Run it only after the release of a commit that carries this code and a renewal on that release, because the served image and the renewal job must both accept the extended expiry before a policy carries it.

Three values come out of the finished build and they feed the release plan under exact names. For `ops/deploy/release.py` the same three values land in the `ReleaseIndex` (`42_staging_release_v3`) as `commit`, which must be the forty character revision, and `engine_image`, which must start with `IMAGE_REGISTRY` (`us-central1-docker.pkg.dev/ogilvy-trends-v2/intelligence-42/`) and match `<name>@sha256:<64 hex>`; `resource_manifest_sha256` is the digest the manifest step proved inside the image. `verify --release-index` then requires the adapter byte reader to return bytes whose SHA256 equals each recorded digest.
