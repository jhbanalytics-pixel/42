# Managed scheduler runtime

R05 implements the managed runtime locally in `ops/runners/managed_runtime.py`, with the proposed job and scheduler configuration under `infra/runtime/` and the contract tests in `ops/tests/test_foundation_scheduler.py`. Nothing in this task creates a native job, scheduler, IAM binding or image. The runtime exports a paused proposal that D04 completes through its own activation gate. The scheduler firing is never execution authority; every cycle still passes through the existing durable consume and result validators.

## Unattended identity

The daily job runs as the manifest orchestration identity, `intelligence-42-orchestration@ogilvy-trends-v2.iam.gserviceaccount.com`, obtained only through Application Default Credentials from the Cloud Run metadata server. The runtime models credential discovery as an injected function returning a descriptor with exactly the keys `kind`, `source` and `principal`. Only `kind` `attached_service_account` with `source` `metadata_server` is accepted, and its principal must equal the service account in the immutable job configuration, which in turn must equal the manifest orchestration identity. User OAuth, a refresh token file, a service account key file and any host scheduler dependency refuse with their own codes even when the discovery labels itself as ADC, so a silent fallback from the metadata server to a gcloud user credential is caught by inspecting the resolved kind rather than the label. The environment variables `GOOGLE_APPLICATION_CREDENTIALS`, `CLOUDSDK_CONFIG`, `CLOUDSDK_AUTH_ACCESS_TOKEN` and `CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE` refuse before discovery runs, because a credential file or host login must never enter the container.

## Scheduler request

Cloud Scheduler sends `POST https://run.googleapis.com/v2/projects/ogilvy-trends-v2/locations/us-central1/jobs/intelligence-42-daily-staging:run` with an OAuth token for `intelligence-42-scheduler@ogilvy-trends-v2.iam.gserviceaccount.com` under the `https://www.googleapis.com/auth/cloud-platform` scope, the header `Content-Type: application/json`, and the body `{}`. The REST representation of `httpTarget.body` is a base64 encoded string, so the two UTF-8 bytes of `{}` are stored as `e30=`. No validation payload, override, argument or environment value travels in that request; the runtime takes every invocation field from the image-bound configuration. Overrides would need the separate `run.jobs.runWithOverrides` permission, which the scheduler identity must not be granted.

Both scheduler jobs are proposed in state `PAUSED`, `timeZone` `Etc/UTC`, `attemptDeadline` `180s`, and `retryConfig` `{"retryCount": 0, "maxRetryDuration": "0s"}`, which the reference describes as no retry of a failed attempt. The daily schedule string in the file is a placeholder that D04 replaces with the approved cutoff schedule before activation. The price policy scheduler fires the separate `intelligence-42-price-policy-staging` job at `0 */12 * * *` UTC and activates only under the C04 renewal grant.

## Invocation contract

`validate_invocation(payload, resources)` accepts a payload with exactly the keys `job_resource`, `resource_manifest_digest`, `mode` and `request_id`. Any missing, extra or malformed field, including an override block or a credential file path, refuses with `invocation_fields_invalid`, so the empty payload of the plan regression is never a successful empty run. The job resource must be the exact full name of the daily staging job; a production job, a sibling staging job, a project number alias or an execution path refuses with `invocation_target_forbidden`. The manifest is validated by the existing `ops/deploy/resource_guard.py` and must grant `invoke` and `read` on that job. The digest must equal the SHA256 of the canonical JSON bytes of the manifest, which for the reviewed manifest `33ed5155608920fddc36e199e77a3082b381b65c3dcd0d803f201811571f1e09` is also the digest of its file bytes, because that file is stored canonically.

`build_invocation(job_config, resources, execution_name, execution_reader=..., credential_discovery=..., environment=...)` is the only producer of that payload inside the container. It validates the closed job configuration, requires `execution_name` to be the `CLOUD_RUN_EXECUTION` short identifier, refuses `MANAGED_RUNTIME_*` variables and a `CLOUD_RUN_JOB` value naming another job, refuses credential files, builds the payload from the configuration and validates it, checks the approved identity and the attached principal, and then confirms the parent job through the injected native readback of the execution and the job before any authority is consumed. The readback must show the same execution name, the daily job as parent, identical execution and job templates, the runtime configuration digest in the job template annotation `42.ogilvy/runtime-configuration-sha256`, the configured service account, zero retries, one task, the configured command and arguments, and a digest pinned image under the configured repository. The returned invocation carries the four payload fields plus `execution_name`, `job_name`, `principal`, `credential_source`, `configuration_sha256`, `scheduler_configuration_sha256`, `image_uri` and `service_account`.

| Refusal | Code |
|---|---|
| Schema, empty payload, override or credential field, malformed value | `invocation_fields_invalid` |
| Unknown mode | `invocation_mode_invalid` |
| Production or other job target | `invocation_target_forbidden` |
| Manifest fails the guard, or lacks invoke or read | `resource_manifest_invalid`, `resource_action_forbidden` |
| Manifest digest does not match the loaded bytes | `resource_manifest_digest_mismatch` |
| Missing or invalid `CLOUD_RUN_EXECUTION` | `execution_identity_missing` |
| Environment override, execution template differs from job template | `runtime_override_forbidden` |
| Credential file or host login variable | `credential_file_forbidden` |
| User OAuth, refresh token file, silent ADC fallback to a user | `credential_source_user_oauth` |
| Service account key file | `credential_source_file` |
| Host scheduler dependency | `credential_source_host_dependency` |
| Discovery raised, or descriptor malformed | `credential_source_unavailable`, `credential_source_invalid` |
| Principal differs from the approved identity | `principal_mismatch` |
| Readback denied, or unavailable | `execution_readback_forbidden`, `execution_readback_unavailable` |
| Execution belongs to another job or another execution | `execution_job_mismatch`, `execution_identity_mismatch` |
| Job annotation does not bind this configuration digest | `runtime_configuration_unbound` |
| Job settings drift from the configuration | `runtime_configuration_mismatch` |
| Image not pinned by digest under the approved repository | `image_unbound` |

## Modes

`run_managed_mode(invocation, authority=..., metadata_reader=..., run_manifest_loader=..., handoff=...)` re-checks the invocation and dispatches on its mode. `verify-runtime` reads approved staging metadata through the injected reader, returns a receipt with the attached principal and the bound digests, and never touches the authority adapter, a vendor or a model. `daily` is gated by the reviewed configuration, not by a refusal on the production path, and this sentence states exactly which is which. The daily job ships with `mode` set to `verify-runtime` in `infra/runtime/daily-staging.json`, and the invocation binds that file's digest, so reaching daily mode at all is a reviewed edit of a digest bound file. Once the mode says `daily`, the two refusals the code raises cover two shapes only: `daily_wiring_unavailable` when no daily wiring is bound, when one of its callables is missing or when an engine daily module is absent, and `stage_adapter_unavailable` when a bound wiring still carries the explicitly unavailable stage seam. Neither covers the shape the runtime ships for itself: `main` builds `default_daily_wiring` for every daily invocation with `native_stage_handlers` as its `stage_handlers`, and `_daily_wiring` rebinds that seam over the wiring's own clients rather than refusing, so on the production path, with the engine daily modules importable, a daily invocation proceeds into the daily cycle. Read the guard as the mode being a reviewed edit, never as the daily schedule being unable to run. D04 owns the two refusals above. When D04 instead supplies a versioned run manifest loader and a handoff, the runtime takes the handoff path below. With D04 installed the runtime reads the existing operation for the request identifier first: a terminal record with known usage is returned as a duplicate trigger without a new launch, and any other existing record refuses with `operation_usage_unknown`. An unresolved previous operation for the job refuses with `operation_unresolved`. The run manifest must carry an operation and a manifest digest, after which the runtime calls `authority.reserve`, `authority.consume` and the handoff with that exact invocation, manifest and consumption.

The authority adapter is the seam to the existing durable controls. `engine_authority_adapter()` binds `reserve` to `_load_execution_authority` and `consume` to `_consume_execution_authority` in `engine/src/analysis/open_intelligence/execution_approval.py`, imported lazily so the unit tests need no engine import. Its operation state readers refuse with `operation_state_unavailable` because D04 owns the daily store. The runtime writes no local completion file and keeps no budget ledger of its own.

## Configuration files

`infra/runtime/daily-staging.json` holds the two Cloud Run job proposals under `jobs`, keyed by job identifier, with `runtime_job` naming the entry the managed runtime serves. Each entry declares the full job resource, the mode (`verify-runtime` for the daily job today, `null` for the price policy job), the service account, the image repository, command, arguments, environment, zero retries, one task, parallelism one and a timeout in seconds. The root binds `resource_manifest_sha256` and `scheduler_configuration_sha256`, so the runtime, the manifest and the scheduler file form one digest chain. `infra/runtime/scheduler-staging.json` holds the two Cloud Scheduler job resources in API field names plus a proposal block per scheduler. Both files are canonical JSON, sorted keys with compact separators and no trailing newline, so their canonical digest equals their file digest and any edit changes the digest the runtime binds into the invocation. Changing the daily job mode to `daily` is an edit to this file and therefore a reviewed deployment change, never a scheduler override.

The `daily_profile` in that file carries no recurring grant digest and no approval phrase digest. The grant binds the image digest in `permitted_image_digests` and the cycle refuses an image the grant does not list, so an image pinning its own grant could never be built. The owner instead renders the grant from the built image digest (`python -m ops.runners.daily_grant_pointer render IMAGE_DIGEST VALID_FROM SEQUENCE OUTPUT_DIR`), records its approval through the approve routine, and creates two objects in `ogilvy-trends-v2-execution-approvals-staging` under a generation match of zero: the grant object at `42/daily/grants/<grant digest>.json` and a pointer at `42/daily/grants/pointers/<image digest hex>/<number>.json` naming the grant digest and the approval phrase digest. At start the daily cycle reads the pointers for the image it runs as, numbered from `000001`, up to the first absent one and at most 64; every pointer read must be the exact canonical document for this job, this image and its own number. No pointer refuses `grant_pointer_missing` and an altered one `grant_pointer_invalid`, both before the grant is read or anything is claimed. The latest pointer's pins join the image profile into the profile the cycle runs. The grant loader still reads the approval only through the durable reader and requires the pointer's phrase digest, the grant's issuing principal and the grant digest; a grant that does not list the running image refuses `recurring_grant_image_forbidden` before any claim. A later grant for the same image is a new pointer at the next number, never a replacement. The daily account reads `42/daily/grants/` and cannot create, replace or delete anything there, so the pointer, like the grant object and its revocation marker, is the owner's.

The price policy entry runs `python -m ops.deploy.refresh_question_policy renew-unattended` with the release index and the unattended grant pinned by generation; both generations read `pending` until the objects exist, and the job refuses before any native call until they are written in (see the pricing renewal section of `release.md`). The reviewed manifest lists a Cloud Scheduler resource for both jobs; the row for `intelligence-42-price-policy-staging` was added by amendment a of R03_DECISIONS_APPROVAL_20260913.json, so both schedulers can be created against the manifest.

## Creating the paused schedulers

`ops/deploy/runtime_schedulers.py` is the scheduler half of the native creation step, with three commands run in the order `plan`, `apply`, `readback`. It uses `ops/deploy/runtime_native_adapter.py`, which sends Cloud Scheduler v1 and Cloud Run Admin API v2 requests over one injectable HTTP transport, so the request the tests see is the request that runs and no mutation shells out. That adapter's call table is closed and has no delete or update call and no general resume call, so no command in this package can rewrite a scheduler that already exists. Its one resume call is pinned to the price policy scheduler: any other name, the daily scheduler's included, refuses with `scheduler_resume_unapproved` before a URL exists, and only the separate resume command described below uses it. The call table holds because every resource name is validated against its own grammar and pinned to the approved project and region before a URL exists: a name carrying a verb colon, a fragment, a query separator, a percent escape, an extra path segment, whitespace, a control character or another project refuses with `resource_name_invalid`, and each URL is built from the endpoint, the pinned location and the validated identifier rather than by concatenating a document's string onto an endpoint. The adapter carries its own transport, which follows no redirect, so a bearer token is never replayed to a redirect target; a 3xx, a response that arrived from another URL, a body that does not parse as a JSON object and a transport result with no status are each refused rather than read as a result.

`plan` loads the runtime file, binds the scheduler file and the resource manifest to the digests that file names, and refuses a scheduler whose declared state is not `PAUSED`, whose OAuth identity is not the manifest scheduler identity, or, for the price policy job, whose cadence is not the approved `0 */12 * * *`. Each scheduler resource passes the resource guard for `deploy` and `read` and each target Cloud Run job for `invoke`. The approved provisioning delta supplies the `roles/run.invoker` rows the scheduler identity needs on both jobs; a missing row refuses with `invoker_binding_missing` and an unapproved delta with `iam_delta_unapproved`. The plan carries those rows as the permission proof obligation and seals itself with a digest over its canonical bytes.

Cloud Scheduler treats a job's state as output only, so a created job is born enabled. `apply` therefore describes first, creates only an absent job, pauses it with its own request, and describes again; only that confirming read lets the receipt record `PAUSED`, and no receipt says `applied` while any scheduler the command touched reads back anything but `PAUSED`, which refuses with `scheduler_not_paused`. An existing job is never created again and is never rewritten: found paused it is recorded as `already_exists` and nothing is sent for it, and found running it is paused with the same pause request and confirmed, which is recorded as `paused`. A confirming read that finds nothing refuses with `scheduler_absent_after_create` or `scheduler_absent_after_pause`. `apply` and `readback` re-derive what the plan asserts rather than trusting it: each scheduler name and create body name is the derived one for its job or the command refuses `scheduler_name_unpinned`, each target URI is the job's own `:run` URI or it refuses `scheduler_target_unpinned`, each OAuth identity is the manifest scheduler identity or it refuses `scheduler_identity_mismatch`, the three recorded digests are re-checked against the reviewed files, and the resource guard runs again over every resource before anything is sent. The content of each scheduler is re-derived the same way rather than read out of the plan: both commands load `infra/runtime/scheduler-staging.json` at the digest the runtime file binds, through the loader that pins the state, the time zone, the cron grammar, the retry configuration, the attempt deadline, the closed key set on the HTTP target, the method, the headers, the token keys and scope and the empty target body, and the create body `apply` sends and the expected document `readback` diffs against are that loaded entry. A plan whose copy of a job differs from the file in any of those fields refuses with `scheduler_entry_unsealed` before a request goes out, so a resealed plan cannot choose the schedule, the retry count, the attempt deadline, the headers or the target body of a scheduler it creates. That scheduler file is the module constant on every sending path, so no path keyword can move the content anchor. A confirming read that answers for another resource name refuses with `scheduler_name_unconfirmed`. A plan whose digest moved refuses with `plan_digest_mismatch`, a plan whose shape, keys, project, parent, expected state, operation sequence or invoker rows are not the reviewed ones refuses with `plan_invalid` rather than raising, apply stops at the first failed operation, and `--dry-run` renders every request through the same request builder from those loaded entries and sends none, so the artifact an operator reads before letting apply touch a billing project is built the way apply builds what it sends rather than echoing the plan document. The dry run renders the whole run, both creates and both pauses, and does not perform the describe precheck, so against a project where one scheduler already exists apply sends fewer requests than the dry run shows; it never shows fewer than apply sends. A refusal raised after a request has already gone out still writes its document to the output path: a receipt whose state is `refused`, naming the refusal, the per scheduler result reached so far, the list of mutations sent and the full adapter record, so a partial apply never leaves a created scheduler with no artifact naming it. Read `record` and `sent` in that receipt, not `schedulers`: `schedulers` names only the jobs whose create, pause and confirming read all completed, so a scheduler created a moment before the refusal appears in `record` and `sent` and not there, and the receipt carries that sentence itself under `read_this_first`. A transport that never answered at all, a read timeout, a reset connection, a name resolution failure or a TLS failure, is one of those refusals and writes the same receipt rather than ending the process with a traceback. The record names each request from the moment it left the client, so a request whose answer was a redirect, was not JSON or never arrived is still named, without a status. The output path is checked before the first request goes out, refusing `output_exists`, `output_directory_absent` or `output_directory_unwritable` while nothing has been sent, because a refusal to write after two creates prints a refusal an operator reasonably reads as nothing happened. If the path is taken by the time the document is written anyway, the document is written to a sibling path named in the command's own output rather than discarded. A refusal raised before any request writes nothing. `readback` describes each scheduler and diffs name, description, schedule, time zone, attempt deadline, retry configuration and HTTP target against the plan, reporting an absent job, a refused read or a running schedule as drift rather than a match, and it carries the three digests it was read against so the handoff can bind it. The diff is taken field by field inside the retry configuration and the HTTP target, and each difference is named by its dotted path (for example `retryConfig.maxDoublings` or `httpTarget.oauthToken.serviceAccountEmail`) with its expected and observed values. A describe returns the job as Cloud Scheduler stores it, which drops `retryConfig.retryCount` at 0 and adds retry defaults the file leaves out, so before comparing, a retry field absent on either side gets the default the Cloud Scheduler v1 Job reference states: `retryCount` 0, `minBackoffDuration` `5s`, `maxBackoffDuration` `3600s` and `maxDoublings` 5. The one header allowed on the live job that the reviewed file does not carry is `User-Agent: Google-Cloud-Scheduler`, with exactly that name and value. Nothing else is reconciled: any other extra header, any other value of those fields, a missing or different `maxRetryDuration`, `attemptDeadline` or token scope, and an absent retry configuration or HTTP target are all drift. Every raw value the defaults alone reconciled is listed under `accepted_service_values` beside `differences`, so an operator can see what was taken as the service's own. `resume` uses the same comparison.

## Resuming the price policy scheduler

`ops/deploy/runtime_scheduler_resume.py` is the one command that starts a paused schedule, and it starts only the price policy scheduler. It is kept out of the `runtime_schedulers` command line on purpose, so `plan`, `apply` and `readback` still hold no command that activates a schedule; its logic and every refusal live in `runtime_schedulers.resume_scheduler`. Run it with the reviewed scheduler plan:

```
python -m ops.deploy.runtime_scheduler_resume --job intelligence-42-price-policy-staging --plan scheduler-plan.json --output resume-receipt.json [--adapter-state adc|owner-gcloud] [--dry-run]
```

What it does, in order. It refuses any `--job` other than `intelligence-42-price-policy-staging` with `scheduler_resume_unapproved` before anything is read or sent, so the daily scheduler is always refused: its activation belongs to another task and its own gate. It checks the output path is free and writable before the first request, as `apply` does. It validates the plan and re-derives the name, the resource and the target from the approved identifiers, re-checks the three digests against the reviewed files and re-runs the resource guard, exactly as `apply` does. It describes the scheduler and requires every compared field (name, description, schedule, time zone, attempt deadline, retry configuration and HTTP target) to equal the reviewed scheduler file's entry under the same comparison `readback` uses, refusing `price_policy_scheduler_drifted` otherwise, and requires the state to be `PAUSED`. A scheduler found `ENABLED` with its fields intact is reported as `already_enabled` and nothing is sent; any other state refuses with `price_policy_scheduler_not_paused`, and an absent scheduler refuses with `price_policy_scheduler_absent` rather than being created. It then reads the target Cloud Run job and refuses with `price_policy_job_absent` when it is missing, or `price_policy_job_unconfirmed` when the read answers for another job, because a scheduler that points at a missing job must not go live. Only then does it send exactly one Cloud Scheduler v1 `jobs:resume` request, a `POST` with an empty JSON body to `https://cloudscheduler.googleapis.com/v1/projects/ogilvy-trends-v2/locations/us-central1/jobs/intelligence-42-price-policy-staging:resume`, followed by a confirming describe that must read `ENABLED` with the compared fields unchanged, refusing `price_policy_scheduler_not_enabled` or `price_policy_scheduler_drifted` otherwise. It writes a write once receipt with contract `42_runtime_schedulers_resume_receipt_v1`, naming the result, the confirmed state, the mutations sent and the full adapter record. A refusal after the resume request went out still writes a receipt whose state is `refused`, because the schedule may already be live; a refusal before it writes nothing. `--dry-run` renders the same four requests through the same request builder and sends none.

What it does not do. It never resumes the daily scheduler, never creates, pauses, deletes or rewrites a scheduler, never runs a Cloud Run job and never changes an IAM binding. It does not pause the scheduler again after a refused confirmation: the receipt names what was sent, and `apply` is the command that pauses a running scheduler. Cloud Scheduler has no conditional resume, so a change made to the scheduler between the checking read and the resume is resumed with it; the confirming read then refuses `price_policy_scheduler_drifted` with the scheduler left enabled, and the operator pauses it with `apply`. The permissions it uses are reading and resuming the scheduler and reading the Cloud Run job, which the identity that runs `apply` and `readback` already holds when it is the project owner.

## Preflight and the D04 handoff

`ops/deploy/runtime_preflight.py` runs the attended proof and exports the package D04 consumes. `trigger` reads the immutable Cloud Run job first and refuses before any mutation unless the job's bound mode is `verify-runtime`, its execution template annotation carries this configuration digest, its service account is the manifest orchestration identity, its command, arguments, environment, retries, task count and parallelism match the configuration and its image is pinned by digest under the approved repository. Only then does it send the actual empty RunJobRequest, whose recorded body is the two bytes `{}`. The output path is checked before that request goes out, and a refusal after it writes a refusal receipt naming every request sent and the adapter record, so a run request that left the client is never left with nothing naming it. Changing the job to the daily mode stays an edit of the runtime configuration and a reviewed deployment change; no preflight flag can do it.

`confirm` reads that operation through R04's `wait_operation`, so a terminal failure stops at once and a deadline reached without a terminal state is `execution_unproven`, never a verified runtime. A read the endpoint answered with a refusal, a refused redirect or a response that arrived from another URL ends that loop after one read rather than being polled as an unknown state, so a persistent denial is a refusal by name instead of a deadline spent replaying an authenticated request. Before it reads anything it re-checks the trigger receipt: its contract, its status, its job name, the configuration digest it was taken against, its operation name against the operation grammar, and its image against the pin rule, so a document cannot choose the URL that is read or carry a floating tag past the trigger. It then reads the execution itself and requires the same execution identity, the daily job as parent, the configuration digest in the execution annotation, the attached orchestration principal, the same pinned image, a completed single task, and every template field that must not change: service account, retries, timeout, task count, parallelism, command, arguments and environment, compared field by field so a field the API populates on its own answer is not read as an override while a changed one still is. The receipt it writes is deterministic and names the operation, the execution, the principal, the credential source, the pinned image and the three bound digests.

`handoff` exports the R05 package: the approved runtime resource manifest digest, the daily job resource and its allowed actions, the attached principal and credential source, the pinned image, the invoker permission observed on each job's own IAM policy, both scheduler states and the digest of the verify-runtime receipt. It refuses a receipt that is not a verified runtime, that is bound to other digests or whose image is not pinned by digest under the approved repository, a scheduler readback that drifted, and a job policy that does not actually carry the invoker row for the scheduler identity. The scheduler readback is bound to the chain it claims: `handoff` is given the scheduler plan beside it as `--scheduler-plan`, validates and reseals that plan, binds that plan's three digests to the reviewed files themselves so a plan that could never have applied is not evidence either, and then requires the readback's key set to be the closed one the readback command produces, its plan digest to be the digest of that plan rather than a well shaped string, its manifest and scheduler file digests to match the verify receipt, its runtime digest to match the runtime file it was read against, and a record whose only calls are two successful reads of the two pinned scheduler resources, each answering `PAUSED` under a URL built from the resource name it reports; anything else refuses with `scheduler_readback_unbound`. What that closes is the accidental mismatch, a readback of one chain paired with a plan or a receipt of another. It does not close a readback typed by hand: every value checked is a value the document carries, so a readback written by hand with the real digests and a record naming the two real reads is accepted. Closing that needs evidence this command does not hold, either the handoff performing the two describes itself over the adapter or the readback carrying a signature over its own bytes that the producer made and this command verifies; neither is done, and the package should be read with that in mind. The package names that plan digest and the digest of the readback itself. Before writing, the producer reads the package back through its own canonical encoding and recomputes the digest the way a reader would, refusing `handoff_invalid` if it does not hold. That is an encoding check on the producer's side and not evidence for anyone downstream: the only thing that proves the package was not edited after it was written is a reader recomputing the digest over the bytes it read. The package records that both schedules remain paused behind the D04 and C04 gates; it grants nothing.

## What remains native

Native preflight must build the image through the R02 gate, create the jobs with the configuration digest annotation and the pinned image, create both schedulers paused, grant the scheduler identity `run.jobs.run` on the daily job and the orchestration identity permission to read its own execution and job, and then run `verify-runtime` through the real RunJobRequest path and read back principal and terminal execution. Every one of those steps now has its reviewed command and its offline proof, and none of them is natively proven by this task: the commands above have never been sent to a real endpoint from here, no receipt in this repository records a created scheduler, a triggered execution or an observed principal, and the handoff package cannot be emitted until those receipts exist.

The job creation step of that list is now a reviewed tool, `ops/deploy/runtime_jobs.py`, with three commands run in the order `plan`, `apply`, `readback`. `plan` validates `infra/runtime/daily-staging.json` through the runtime loader, requires its manifest digest to equal the engine copy of the resource manifest, binds the image to a successful build record that pushed exactly one image with the given digest, passes every job resource through the resource guard for `deploy` and `read`, renders one create operation per job as a `gcloud run jobs replace` specification carrying the pinned image, the service account, command, arguments, environment, zero retries, one task, parallelism one, the timeout and the two annotations `42.ogilvy/runtime-configuration-sha256` and `42.ogilvy/resource-manifest-sha256`, attaches the job bindings that `ops/deploy/iam_delta_v1.json` holds for those jobs, refuses `iam_delta_unapproved` while that delta's `approval.state` is `proposed` rather than `approved`, and seals the plan with a digest over its canonical bytes. A describe precheck precedes each create so an existing job is recorded as `already_exists` and never replaced; the precheck reads the SDK's own `Cannot find job` sentence as absent. `apply` refuses a plan whose digest or operation shape has moved, re-checks the guard for `deploy` and `read`, runs the operations through the given gcloud executable with an argument list, no shell and the plan file's directory as working directory, stops at the first failure, and writes a receipt naming the plan file and carrying the exact argument vector, exit code and output tails of every operation; with `--dry-run` it prints the argument vectors and writes nothing. `readback` describes each job and its IAM policy and diffs image, service account, command, arguments, environment, timeout, retries, task count, parallelism, annotations and bindings against the plan, recording a refused read as `refused`. The scheduler stays paused throughout, no command touches it, and no command runs a job.

A job that already exists is never touched by `apply`, so bringing one to a new plan is a fourth command, `replace --plan <plan.json> --job <job id> --output <receipt.json> --gcloud <gcloud> [--dry-run]`. It refuses `output_exists` before any call and a plan whose digest does not verify. It describes the live job (`job_absent` when there is none; it never creates one) and compares it with the plan's entry for that job: every compared field other than image, args, env and the two configuration annotations must already equal the plan, or it refuses `replace_field_not_allowed` naming the fields, so the service account, command, timeout, retries, task count and parallelism are never changed by it. A live env entry that is not a plain name and value, such as a secret reference, refuses `job_env_not_plain`, because the plan's env would drop it. A job already matching the plan ends `unchanged` with nothing sent. Otherwise the replacement is the live job with only those four fields changed: resources, volumes and every other part of the live spec are carried as read, the output only status and the server's creator, modifier and operation annotations are left out, and `metadata.resourceVersion` is the version read. The dry run prints the changed fields with expected and observed values, the replacement and the replace argv, and sends nothing but the one describe. A real run writes the replacement beside the receipt, describes the job again and refuses `job_changed_since_read` if the version moved, then sends one `gcloud run jobs replace`; a server conflict on the version (gcloud's HTTPError 409 or Conflict for resource, the status token ABORTED or a modified object; a dropped connection is not one) is reported as `job_changed_since_read` and not retried, and any other failure other than a refusal is read back and the live fields recorded, because a timed out replace may still have landed. Execution tokens on the live job are not sent back. It reads the job back and ends `replaced` only when every compared field equals the plan and everything it carried (the rest of the spec, the job labels and the job annotations, less the gcloud client stamp, labels under `run.googleapis.com/` and the creator, modifier and operation annotations the server sets) is as it was before, `replace_unverified` with `readback_mismatch` or `carried_fields_changed` otherwise. It never deletes a job and never reads or writes IAM. Whether Cloud Run enforces the carried `resourceVersion` on replace is not natively proven from here; the second describe is the guard that is.
